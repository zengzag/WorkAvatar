# WorkAvatar 实现方案

> 供智能体快速了解项目核心架构与实现。

## 1. 技术架构

**进程模型**：Electron 双进程 — `electron/` 主进程（Node.js）+ `src/` 渲染进程（React）。通过 `contextBridge` 暴露 `window.electronAPI`，IPC 通道按模块定义在 `electron/shared/channels/`。

**技术栈**：
- 前端：React 18 + Ant Design 6 + Zustand + i18next
- 后端：better-sqlite3（WAL 模式 + 性能 PRAGMA 调优）+ OpenAI 兼容 LLM API
- 数据库：主库（员工/技能/LLM配置）+ KMS 主库（workavatar-kms.db：索引/FTS5/段落/摘要）+ KMS 向量库（workavatar-kms-vectors.db：embedding/vec0 虚表，独立分库减小主库体积）
- 批量索引：worker_thread（把 better-sqlite3 同步阻塞操作移出 Electron 主线程，避免解析大库时 UI 卡死）
- 构建：Vite + electron-builder

**版本与构建元信息管理**（统一由 `build-info.json` 维护）：
- `scripts/generate-build-info.mjs` 自动收集 `package.json` 版本号 + `git rev-parse --short=7 HEAD` 短哈希（带 `-dirty` 标记未提交修改）+ 当前 ISO 时间，写入项目根 `build-info.json`
- `package.json` 通过 `predev` / `prebuild` 钩子在 `vite` / `electron-builder` 启动前自动调用，开发者无需手动维护
- 渲染进程：`vite.config.ts` 的 `define` 注入 `__APP_VERSION__` / `__APP_COMMIT__` / `__APP_BUILD_TIME__` 三个全局常量，AboutSection 直接读取显示 `0.1.0(b440b54)` 与构建时间
- 主进程：`electron/main/index.ts` 的 `readBuildInfo()` 在启动日志中打印完整版本/提交/构建时间，dev 读 `process.cwd()/build-info.json`，打包后读 `app.getAppPath()/build-info.json`（electron-builder `files` 列表已包含 `build-info.json`）
- `build.ps1` 第 1 步显式调用 `node scripts/generate-build-info.mjs` 作为打包前必做环节；`build-info.json` 已加入 `.gitignore`，避免污染仓库

## 2. KMS 本地资料库搜索引擎

独立模块，位于 `electron/main/services/kms/`。统一管理**目录源**（自动跟踪）与**合集**（手动挑选），支持独立桌面搜索或作为检索组件接入 Agent。

### 子服务

- **kms-database** — 索引目录、文件注册表、FTS5 全文索引、冷热数据、合集摘要（主库 workavatar-kms.db）+ 向量嵌入/vec0 虚表（向量库 workavatar-kms-vectors.db，独立分库）；含 PRAGMA 性能调优、WAL checkpoint 接口、事务包装工具、向量库迁移逻辑
- **kms-crawler** — 目录扫描、文件变更检测、增量索引、访问统计；变更检测采用两阶段优化：Phase1 仅用 readdirSync+statSync+mtime/size Map 双向对比（瞬时，无文件读取），Phase2 对候选文件并行计算 SHA-256（并发 16，近线性加速）；无候选变更时跳过哈希阶段直接返回；DB 查询只投影 5 个必要字段（id, file_path, file_hash, modified_time, file_size）
- **kms-tokenizer** — 中文分词服务（基于 @node-rs/jieba），索引侧精确模式切词、查询侧搜索引擎模式切词
- **kms-search-engine** — FTS5 + 向量语义 + 文件名 LIKE 三路搜索，混合搜索以 RRF 倒数排名融合（关键词 / 语义 / 文件名），支持时间范围/扩展名/合集过滤；embedding 读写走 vectorDb 连接
- **kms-index-manager** — 全量/增量/重建索引、向量嵌入生成、冷热数据升降级、合集深度处理
- **kms-index-worker-client** — Worker 线程客户端，把批量索引/合集深处理任务路由到 worker_thread，避免 better-sqlite3 同步阻塞主线程；Worker 不可用时降级为主线程直接执行
- **kms-search-agent** — 检索子智能体（查询分类→路径规划→多轮检索→结果提纯）
- **kms-file-reader** — 文件读取、段落/TOC 查询、按偏移/行号定位
- **kms-mcp** — MCP 服务（Streamable HTTP，8 个工具暴露给第三方智能体）
- **kms.service** — 顶层外观服务

### 核心机制

**冷热数据分层**：
- 冷数据：文件名 + 关键词索引 + 轻量摘要（文件头500字符，不调 LLM）
- 热数据：LLM 摘要（150字+关键词+主题）+ 段落索引 + 向量嵌入
- 晋升：30天内搜索命中≥15次或读取≥8次（高频使用才升级，避免一搜索就变热数据）
- **搜索命中计数限制**：仅记录排名靠前的前10条结果作为命中（`SEARCH_HIT_RECORD_LIMIT = 10`），避免 topK/resultLimit 过大时大量低相关结果被计入命中导致文件被轻易晋升；AI 智能检索与普通搜索均适用
- 降级：90天无访问
- **晋升后自动重新解析**：`KMSIndexManagerService.evaluateAndPromote()` 对晋升的冷文件自动执行热数据处理流水线：
  - 受 `searchParams.autoReparseHotData`（默认开启）控制：关闭后仅完成层级晋升（data_tier=hot），不触发重新解析与摘要
  1. file2md 重新解析（覆盖原 cold 解析结果）
  2. 删除旧索引 + 重建索引（标题、内容段落、parse_mode、轻量摘要，合并为单事务）
  3. `processHotFile()`：LLM 目录分析 + 段落切分 + 段落摘要 + 文件摘要
  4. `generateEmbeddingsForFile()`：为该文件生成向量嵌入
  5. PASSIVE checkpoint 合并 WAL
- **Worker 线程执行**：晋升处理通过 `KMSIndexWorkerClientService.runTask('processPromotedFiles', ...)` 路由到 Worker 线程，避免 file2md 同步原生解析阻塞 Electron 主线程导致 UI 卡死；Worker 不可用时降级为主线程直接执行
- **触发时机**：搜索命中后异步触发（fire-and-forget），普通搜索和 AI 智能检索都会触发；索引流程结束后强制触发（force=true）
- **去抖**：`MIN_EVALUATION_INTERVAL_MS = 5min`，5分钟内的多次搜索只触发一次评估；`force=true` 跳过去抖（用于索引完成后的立即评估）
- **并发控制**：`promotionRunning` 标志位避免并发晋升；Worker 内部维护独立 `promotionAbort` 信号，主线程通过 `cancelPromotion()` 消息取消
- **内容读取优化**：`KMSFileReaderService.getStoredFullContent(fileId)` 优先从 `kms_paragraphs.content` 拼接读取热数据全文，零解析开销；冷数据（无段落记录）回退到按 `parse_mode` 重新解析（file2md→hot，其他→cold），`getFileContent`/`getFileFullContent`/`readFileChunk` 均已适配

**检索子智能体**（6阶段闭环）：
1. 查询类型识别（locate/concept/trend/analysis）
2. 获取文件清单 + 目录摘要
3. 检索路径规划（1-3组关键词 + 候选文件）
4. 多轮检索执行
5. 信息补充（最多5个文件片段，每段2000字符）
6. 结果提纯（结论≤500字 + 精准溯源：文件路径/页码/行号/偏移）
- LLM 不可用时降级为单次混合检索 + 关键词摘要
- 中间进度通过 `KMS_AGENT_SEARCH_PROGRESS` 事件实时推送

**合集深度处理**（9阶段，非阻塞后台执行）：
文件解析 → 段落切分 → LLM 目录恢复 → 目录章节生成 → 段落摘要 → 文件摘要 → 段落向量化 → 合集摘要 → 合集摘要向量化
- 进度通过 `KMS_INDEX_PROGRESS` 推送，含 `collectionId`/`collectionName`/`fileId`
- 支持取消，所有阶段检查 `AbortSignal`
- **增量处理**（`incremental=true` 默认开启）：跳过 `data_tier='hot'` 且已有 LLM 摘要（`kms_file_summaries.summary` 非空）的文件，仅处理新增或未完成深处理的文件；当所有文件均已处理时，前端弹出确认询问是否强制全量重处理（`incremental=false`）；增量模式下若无待处理文件但合集摘要缺失，仍会补充生成合集摘要
- **单文件深度处理**（`processSingleFileDeep`）：合集文件列表中每行提供"深度处理此文件"按钮，独立处理单个文件；`listFilesInCollection` 返回 `deep_processed` 字段（`data_tier='hot' AND summary != ''` → 1）用于状态展示；`getCollectionStats` 返回 `deepProcessedCount` 统计已处理文件数；IPC 通道 `KMS_PROCESS_FILE_DEEP`

**MCP 服务**：
- 协议：Streamable HTTP（POST /mcp），兼容 2025-03-26
- 暴露 8 个工具：`kms_list_sources`、`kms_stats`、`kms_search`、`kms_agent_search`、`kms_get_content`、`kms_get_summary`、`kms_get_toc`、`kms_get_paragraphs`
- 30 分钟无活动 session 自动清理

**搜索性能优化**：
- **中文分词**：基于 `@node-rs/jieba`（Rust jieba-rs N-API 绑定，预编译二进制无需 node-gyp）
  - 索引侧：`kmsTokenizer.segment()` 精确模式切词，写入 FTS5 前将连续中文切分为空格分隔的词序列，使 `unicode61` tokenizer 按空格建立正确 token 边界，BM25 排序基于真实词粒度
  - 查询侧：`kmsTokenizer.segmentForSearch()` 搜索引擎模式切词，对长词进一步切分子词提升召回率，替代原 bigram 滑动窗口方案（避免 MATCH 表达式过长与前缀扫描开销线性增长）
- **embedding 缓存**：`LRUBoundedCache` 类替代原无上限 `Map`
  - 总字节上限 256MB（覆盖约 8 万条 768 维向量），超限时按 LRU 顺序淘汰最旧条目
  - 单条目超限时拒绝缓存（避免缓存命中率为 0 的无效占用），向量检索回退到 DB 全量加载
  - 支持 `update` 接口原地修改并重算字节（用于 storeEmbedding/storeEmbeddingsBatch 增量写入）
- **混合排序**：RRF（Reciprocal Rank Fusion）替代原线性加权
  - 公式：`score = 1/(k + fts_rank) + 1/(k + vec_rank) + 1/(k + filename_rank)`，k=60（Cormack et al. 2009 标准值）
  - 三路独立来源：关键词（FTS5，索引正文/标题/段落）+ 语义（向量，768 维 cosine）+ 文件名（LIKE 匹配 kms_files.file_name，键 `file_name-${fileId}` 不与 `file_title-${fileId}` 等冲突）
  - 仅依赖排名位置（1-indexed），无需归一化 BM25 与 cosine 分数，对尺度鲁棒
  - 同时出现在多个来源的文档自然获得更高分数，单一来源命中也有非零分数保留召回
  - 文件名来源（fileNameSearch）复用 dirIds / collectionIds / fileExtensions / timeRange 过滤，键与 FTS/向量键互不冲突，三路独立可同时命中同一文件叠加得分
- **文件路径可搜索**：`indexFileTitle` 将 `fileName + filePath` 写入 FTS5 content 列和 `kms_search_index.content`，使路径中的目录名（如"公文模板"）可被关键词/混合搜索命中；LIKE 降级搜索额外匹配 `f.file_path`；混合搜索的"文件名"来源则直接对 `kms_files.file_name` 做关键词 LIKE，三者互为补充

### 前端

`src/pages/KMS.tsx` 三视图切换：

- **搜索视图**（默认）：关键词/语义/混合/AI 四种模式，默认混合搜索；搜索历史内嵌于输入框（仅存元数据）
- **合集管理视图**：卡片式合集列表，详情抽屉含文件清单（展开行懒加载 AI 内容）
- **知识沉淀视图**：文件摘要 Tab + 统计信息 Tab

### 数据库性能优化（大库场景：3000+ 文件 / 2GB+ 数据库）

针对大库写入卡死、IO 瓶颈问题，进行了三轮重构优化，配合 PRAGMA 调优和事务合并：

**PRAGMA 配置**（`openKmsDb()` 中一次性设置，主库和向量库共用）：
- `synchronous = NORMAL`：WAL 模式下事务提交不强制 fsync，避免每次 commit 等磁盘同步（默认 FULL 是卡死主因）
- `cache_size = -200000`：200MB 页缓存（默认仅 2MB）
- `mmap_size = 268435456`：256MB 内存映射 IO，减少 read 系统调用
- `temp_store = MEMORY`：临时表/索引/排序中间结果放内存
- `wal_autocheckpoint = 2000`：8MB 触发自动 checkpoint（默认 4MB）
- `busy_timeout = 10000`：10 秒 busy 等待（多连接并发写入时等待而非立即抛 SQLITE_BUSY）
- `journal_size_limit = 536870912`：WAL 文件上限 512MB

**事务合并**（`runInTransaction` 工具方法）：
- `kms-index-manager` 主索引循环、`kms-auto-index` 自动索引循环、`kms-index-manager.processCollectionDeep` 合集深处理循环中，原本每个文件单独执行 4-5 次小事务（deleteIndex + indexTitle + indexParagraphs + saveLightSummary 等），3000 文件 = 12000+ 次 commit
- 改造后合并为 1-2 次外层事务，内层 `db.transaction` 自动变成 SAVEPOINT，最终只触发 1 次 commit
- 借助 better-sqlite3 的事务嵌套（SAVEPOINT）机制，无需修改各子方法的内部实现

**WAL checkpoint 控制**：
- 索引流程结束、合集深处理结束、自动索引结束三个位置主动调用 `checkpoint('PASSIVE')`
- `close()` 关闭前执行 `checkpoint('TRUNCATE')`，确保 WAL 内容写回主库文件
- 避免 WAL 文件无限膨胀挤占磁盘

**FTS5 虚表空间回收**（`optimizeFts5Index`）：
- FTS5 的 DELETE 只标记文档为已删除，实际数据仍保留在内部 segment 中；SQLite 的 VACUUM 对 FTS5 虚表无效（只重建普通表 b-tree），无法回收 FTS5 空间
- 重建索引时大量 DELETE+INSERT 会导致 FTS5 segment 持续膨胀，必须通过 FTS5 专有命令回收
- 索引流程结束后自动执行 `optimizeFts5Index('merge')`（轻量级合并 segment）
- `cleanupDatabase` 中执行 `optimizeFts5Index('rebuild')`（完全重建，彻底回收）

#### 重构优化 1：数据冗余消除（kms_search_index.content 截断）

**问题**：`kms_search_index.content` 和 `kms_fts.content`（FTS5 虚表）存储了完全相同的全文内容，导致 3000 文件场景下主库体积翻倍。`kms_search_index` 表用于列表展示和摘要预览（仅需前 500 字符），`kms_fts` 表用于全文检索（需要完整内容建立倒排索引）。

**改造**：
- `kms-search-engine.service.ts` 的 `indexContentParagraphs` 方法中，写入 `kms_search_index` 时将 content 截断为 500 字符（`SEARCH_INDEX_CONTENT_LIMIT`），FTS5 仍索引完整原文
- 列表展示和摘要预览从 `kms_search_index.content` 读取前 500 字符即可满足需求
- 全文检索命中时通过 `kms_fts` 的 `content` 字段获取完整匹配文本
- 减小主库体积约 40-50%，同时减小 checkpoint 时的 IO 压力

#### 重构优化 2：Embedding 分库（向量库独立文件）

**问题**：`kms_embeddings` 表存储 Float32Array 序列化后的 BLOB（每条 768 维 ≈ 3KB），3000 文件 × 平均 50 段落 = 15 万条 ≈ 450MB。这些 BLOB 与主库的 FTS5/段落/摘要数据混在一起，导致：
1. 主库体积膨胀（2GB+），mmap 效率下降
2. 向量 BLOB 写入与 FTS5 读取争抢 IO
3. checkpoint 时需要合并大量 BLOB 数据

**改造**：
- 新增 `path.service.ts:getKMSVectorDbPath()` 返回独立的 `workavatar-kms-vectors.db` 文件路径
- `kms-database.service.ts` 同时打开主库和向量库两个连接，共用同一套 PRAGMA 配置
- `initializeVectorSchema()` 在向量库中创建 `kms_embeddings` 表（无外键约束，跨库外键不可用）
- `migrateEmbeddingsToVectorDb()` 一次性迁移：检测主库是否有旧 `kms_embeddings` 表，分批 500 条迁移到向量库后删除主库中的旧表
- `kms-search-engine.service.ts` 所有 embedding 读写改用 `vectorDb` 连接（initVecIndex/createVecTable/migrateExistingEmbeddings/storeEmbedding/storeEmbeddingsBatch/syncVecIndex/loadAllEmbeddings/loadEmbeddingsFiltered/vectorSearchViaVec0/vectorSearchViaJS/getIndexStats/cloneIndexData）
- `deleteIndexByFile` 拆分为两个独立事务：主库删 fts/search_index/paragraphs，向量库删 embeddings
- `kms-embedding.service.ts` 用应用层 Set 过滤替代原跨库 LEFT JOIN（跨库 JOIN 不可用）：
  - `loadExistingEmbeddingKeys()` 加载向量库所有 `(source_type, source_id)` 到 Set
  - `generateEmbeddings()` 用 keyset 分页（`id > ? ORDER BY id LIMIT ?`）替代 OFFSET，避免大表 OFFSET 性能退化
  - `generateEmbeddingsForFile()` 同样在应用层过滤

**效果**：主库体积从 2GB 降到约 1.5GB，向量 BLOB 写入不与主库 IO 争抢，主库 mmap 效率提升。

#### 重构优化 3：Worker Thread 改造（批量索引移出主线程）

**问题**：better-sqlite3 是同步 API，所有 DB 读写都阻塞主线程。解析 3000 文件时，每个文件涉及解析（CPU 密集）+ DB 写入（同步阻塞）+ LLM 调用（async I/O），主线程被长时间占用导致 UI 卡死。

**改造**：
- 新增 `electron/main/workers/kms-index-worker.ts` Worker 入口，在 worker_thread 中初始化独立的 KMS 服务单例和 DB 连接
- 新增 `electron/main/services/kms/kms-index-worker-client.service.ts` 主线程客户端，懒加载 spawn Worker，暴露 `runTask(task, args, fallback)` 方法
- `vite.config.ts` 新增 Worker 作为第三个 electron 入口，输出 `dist-electron/main/kms-index-worker.js`，共用 nativeExternals 列表（better-sqlite3/sqlite-vec/@node-rs/jieba 等），禁用 codeSplitting 确保单文件输出
- Worker 适配：`path.service.ts` 检测 `!isMainThread && workerData?.dataDir`，从 workerData 读取 dataDir 避免依赖 electron.app；`llm-client.service.ts` 用 `getSafeStorage()` 延迟加载 safeStorage，Worker 模式下从 `workerData.apiKeys` 读取主线程预解密的 API Key
- `kms.service.ts` 的 `buildFullIndex`/`incrementalIndex`/`rebuildDirIndex`/`processCollectionDeep`/`processSingleFileDeep` 五个批量方法路由到 Worker 客户端，同时保留主线程直接执行作为降级路径
- Worker 完成任务后，主线程主动 `invalidateCache()` + `checkpoint('PASSIVE')` 让下一次查询读到最新数据
- WAL 模式允许主线程读 + Worker 写并发，主线程在批量索引期间继续提供搜索/读取服务
- 取消逻辑同时通知 Worker 和主线程降级路径的 AbortController

**消息协议**：
- 主线程 → Worker：`{ type: 'start', id, task, args }` / `{ type: 'cancel' }` / `{ type: 'cancelCollectionDeep' }` / `{ type: 'ping' }`
- Worker → 主线程：`{ type: 'progress', progress }` / `{ type: 'done', id, result?, error? }` / `{ type: 'ready' }` / `{ type: 'fatal', error }` / `{ type: 'pong' }`

**降级策略**：Worker 初始化失败（native 模块加载失败、超时等）时标记 `workerFailed = true`，后续所有批量任务自动降级为主线程直接执行，保证功能可用。

#### 数据库清理与残留数据回收

**问题**：移除索引目录或删除本地文件后，数据库体积不缩小的原因有两点：
1. **残留数据**：
   - `kms_fts`（FTS5 虚表）不支持外键级联删除，删除 `kms_files` 记录后，对应的全文索引条目仍残留
   - `kms_embeddings` 位于独立的向量库（`workavatar-kms-vectors.db`），跨库外键不可用，删除文件后 embedding 记录成为残留
   - 主库的 `kms_paragraphs`/`kms_file_summaries`/`kms_search_index`/`kms_access_log`/`kms_file_collections` 通过 `ON DELETE CASCADE` 自动清理，无残留问题
2. **SQLite 不自动回收空间**：DELETE 只把页标记为空闲，文件体积不会缩小，需 VACUUM 重建文件才能释放磁盘空间

**修复**：
- `kms.service.ts` 的 `deleteIndexDir`：删除目录前先收集所有关联文件 ID，逐个调用 `searchEngine.deleteIndexByFile(fileId)` 清理 FTS5 + 向量库 embedding，再删除目录记录（级联清理主库其余表）
- `kms-crawler.service.ts` 的 `unregisterFile`：删除文件记录前先调用 `searchEngine.deleteIndexByFile(fileId)` 清理 FTS5 + 向量库，再删除 `kms_files` 记录

**数据库清理功能**（`kms-database.service.ts`）：
- `getDatabaseStats()`：返回主库/向量库/WAL 文件大小，及残留 FTS5 条目数、残留 embedding 条目数（跨库用应用层 Set 过滤统计）
- `cleanupDatabase()`：① 删除残留 FTS5 条目（`DELETE FROM kms_fts WHERE file_id NOT IN (SELECT id FROM kms_files)`）② 删除向量库残留 embedding + vec0 虚表行 ③ 清理游离文件 ④ FTS5 rebuild（重建 FTS5 虚表内部 segment，回收已删除文档空间，VACUUM 对 FTS5 无效）⑤ `checkpoint('TRUNCATE')` 把 WAL 写回主库 ⑥ 对主库和向量库分别执行 `VACUUM` 重建文件回收空闲页。返回清理前后体积对比

**IPC 通道**：`KMS_GET_DATABASE_STATS` / `KMS_CLEANUP_DATABASE`，通过 `safeHandle` 注册

**前端 UI**：`KMSIndexPanel.tsx` 的「索引管理」Tab 底部新增「数据库清理」卡片，展示主库/向量库体积 + 残留条目数（有待清理项时高亮警告色），提供「清理数据库」按钮（二次确认 → 执行 → 提示释放空间大小）。VACUUM 是同步阻塞操作，按钮在索引进行中禁用，清理期间数据库短暂锁定

### Office docx 模板/原地编辑能力

`office_exec` 沙箱中除 `docx`（从零创建）外，新增本地模块 `docx-template`（`require('docx-template')`），基于 adm-zip 直接操作 OOXML，解决「基于模板排版生成」与「只改内容不改排版」两类需求。读取 docx 仍用 file2md（转 markdown，丢失排版），需要保留排版时改用 docx-template。

实现位于 `electron/main/services/agent/tools/docx-template.helper.ts`，在 `office-exec.tool.ts` 加载时注入 `OFFICE_MODULES['docx-template']`，通过 `office_guide` 工具向 LLM 输出使用说明。不引入新 npm 依赖（adm-zip 已在依赖中）。

**7 个 API**：
- `listStyles(docxPath)` → 列出 styles.xml 中定义的命名样式 `{styleId, name, type}`
- `inspect(docxPath)` → 列出 document.xml 段落 `{index, styleId, text, formatting}`（含表格内段落）；`formatting` 含 `{font, fontSize, bold, italic, color, alignment}`，从 `<w:pPr>` 与首 run 的 `<w:rPr>` 提取直接格式，用于判断模板类型（formatting.font/fontSize 有值→直接格式模板）
- `renderTemplate(templatePath, {key:value}, outputPath)` → `{key}` 占位符替换，保留全部排版；同时处理正文与页眉页脚；适合两种模板类型
- `createFromTemplate(templatePath, blocks, outputPath)` → 保留模板 styles.xml/页面设置(`<w:sectPr>`)/页眉页脚，用 blocks 重建正文段落；block 排版来源按优先级：cloneFrom > style > 直接格式字段
  - block: `{text, style?, cloneFrom?, font?, fontSize?, bold?, italic?, color?, alignment?, pageBreakBefore?}`
  - `cloneFrom`：从模板指定 index 段落克隆完整 `<w:pPr>` + 首 run `<w:rPr>`，**直接格式模板必须用此字段**（普通 docx 模板通常用直接格式设置而非命名样式）
  - `style`：引用命名样式 ID（直接格式模板无效）
  - `font/fontSize/bold/italic/color`：直接指定 run 级格式（fontSize 单位磅 pt）
- `replaceText(docxPath, {old:new}, outputPath)` → 任意文本查找替换，保留排版（文本级，不改段落数）
- `setParagraphText(docxPath, paragraphIndex, newText, outputPath)` → 替换指定段落文本，保留 `<w:pPr>` 段落样式与首个 `<w:rPr>` run 级排版（单段文本级，不改段落数）
- `spliceParagraphs(docxPath, startIndex, deleteCount, insertBlocks, outputPath)` → **段落级批量编辑**（插入/删除/替换多段），类似 Array.splice；保留未修改段落完整排版，插入段落支持 cloneFrom 克隆原文档段落排版；返回 `{originalCount, deleted, inserted, newCount}` 便于验证。**解决智能体修改文档时因 setParagraphText 无法插入多段而回退到 adm-zip 手动操作 XML 的问题**

**路径保护**：renderTemplate/createFromTemplate/replaceText/setParagraphText/spliceParagraphs 均**禁止 outputPath 与输入路径相同**（基于模板生成/修改文档必须创建新文件，防止覆盖原始文件），路径相同性通过 `path.resolve()` 规范化后比较。

**关键技术点**：
- docx 本质是 ZIP：正文 `word/document.xml`、样式 `word/styles.xml`、页眉页脚 `word/header*.xml`/`word/footer*.xml`
- 段落 `<w:p>` 不可嵌套，用「找下一个 `</w:p>`」扫描方式安全提取（含自闭合 `<w:p/>`）
- 同一逻辑文本可能被 Word 拆分到多个 `<w:t>` run；`replaceTextInXml` 合并所有 `<w:t>` 文本 → 在合并文本上定位匹配 → 回填到 run，替换值只写入首个覆盖 run（保留其 `<w:rPr>`），其余覆盖 run 清空
- 文本处理在反转义空间进行，回写时重新转义；首尾含空白时自动补 `xml:space="preserve"`
- createFromTemplate 替换 `<w:body>` 内部内容为 `新段落 + 原末尾 <w:sectPr>`，保留页面设置与页眉页脚引用
- `extractFormatting` 从段落 `<w:pPr>` 提取对齐 `<w:jc>`，从首 run `<w:rPr>` 提取字体 `<w:rFonts>`（优先 eastAsia 回退 ascii）、字号 `<w:sz>`（半磅→磅）、加粗 `<w:b>`、斜体 `<w:i>`、颜色 `<w:color>`
- `buildParagraphXml` 按 cloneFrom 优先级构建段落：cloneFrom 时用 `extractPPrString` + `extractFirstRunProps` 克隆源段落排版，`applyPPrOverrides` 叠加 alignment/pageBreakBefore 覆盖，`hasRunLevelOverrides` 判断是否用字段重建 rPr 替代克隆 rPr
- `spliceParagraphs` 计算 body 内保留范围边界：`keepBeforeEnd`（删除范围前一段 end，startIndex=0 时用 bodyInnerStart）+ `keepAfterStart`（删除范围后第一段 start，删除到末尾时用 bodyInnerEnd 保留 `<w:sectPr>`），拼接 `xml[0:keepBeforeEnd] + insertXml + xml[keepAfterStart:]`
- **智能体使用引导**（office_guide）：①使用 docx-template 前先 inspect 判断模板类型，直接格式模板用 cloneFrom，命名样式模板用 style；②**docx-template/docx/adm-zip 等模块只在 office_exec 沙箱可用，shell_exec 的 Node 环境未安装**（避免智能体误用 shell_exec 调 node + require 失败）；③修改文档按类型选 API：文本级替换用 replaceText/setParagraphText，段落级编辑（插入/删除/替换多段）用 spliceParagraphs，**不要回退到 adm-zip 手动操作 XML**；④操作顺序：先 office_guide 了解能力 → inspect 定位段落 → 选 API → 输出到新文件 → inspect 验证

**辅助函数**：
- `extractPPrString(content)` → 提取 `<w:pPr>...</w:pPr>` 原始字符串
- `extractFirstRunProps(content)` → 提取首 run 的 `<w:rPr>...</w:rPr>` 原始字符串
- `buildRPrFromFields(block)` → 从 block 的 font/fontSize/bold/italic/color 字段构建 `<w:rPr>`
- `buildPPrFromFields(block)` → 从 block 的 style/alignment/pageBreakBefore 字段构建 `<w:pPr>`
- `applyPPrOverrides(pPr, alignment, pageBreakBefore)` → 在已克隆的 pPr 上替换/插入 `<w:jc>` 与 `<w:pageBreakBefore/>`
- `hasRunLevelOverrides(block)` → 判断 block 是否提供任一 run 级字段（决定是否覆盖克隆的 rPr）

### Office pptx 原地编辑能力

`office_exec` 沙箱中除 `pptxgenjs`（从零创建）外，新增本地模块 `pptx-template`（`require('pptx-template')`），基于 adm-zip 直接操作 OOXML，提供 PPTX 原地文本替换能力。`pptxgenjs` 只能从零创建演示文稿，无法读取/修改已有 pptx，pptx-template 解决「只改 PPT 文字内容不改排版」的需求。

实现位于 `electron/main/services/agent/tools/pptx-template.helper.ts`，在 `office-exec.tool.ts` 加载时注入 `OFFICE_MODULES['pptx-template']`。不引入新 npm 依赖。

**2 个 API**：
- `inspect(pptxPath)` → `{slides:[{slideNumber, texts:[...]}]}`，列出各幻灯片的 `<a:t>` 文本内容
- `replaceText(pptxPath, {old:new}, outputPath)` → 跨幻灯片文本查找替换，在 `<a:t>` 元素内替换文本保留 run 级排版；同时处理幻灯片（`ppt/slides/slide*.xml`）与演讲者备注（`ppt/notesSlides/notesSlide*.xml`）；返回 `{slidesProcessed, replacementsMade}`

**路径保护**：replaceText **禁止 outputPath 与输入路径相同**（基于 `path.resolve()` 规范化后比较）。

**关键技术点**：
- pptx 本质是 ZIP：幻灯片在 `ppt/slides/slideN.xml`，演讲者备注在 `ppt/notesSlides/notesSlideN.xml`
- 文本在 `<a:t>` 元素中（`<a:r>` run → `<a:t>` text），用正则 `/<a:t>([^<]*)<\/a:t>/g` 提取
- 替换在反转义空间进行：提取 `<a:t>` 内容 → unescapeXml → 应用替换 → escapeXml → 回填
- `getSlideEntries` 按数字排序（slide1, slide2, ... slide10）

**xlsx 已有文件修改**：`xlsx` 库（SheetJS）原生支持 `XLSX.readFile()` 读取已有文件 → 修改单元格 → `XLSX.writeFile()` 保存。office_guide 的 xlsx 格式指南包含读取/修改已有 Excel 的代码模板。注意 `readFile` 会丢失部分格式（公式、图表、样式），仅保留值和基本格式。

### office_guide 按格式细分

`office_guide` 支持 `formats` 参数（多选，enum: docx/pptx/xlsx/docx-template/pptx-template）：
- **不传 formats（概览模式）**：返回各格式简要说明 + 通用规则，提示用 formats 获取详细指南
- **传 formats（详细模式）**：只返回指定格式的详细指南（代码模板 + 关键陷阱）+ 通用规则

每个格式的详细指南独立编写，避免相互影响，内容更详尽。通用规则（模块加载状态、文件保存规则、沙箱限制）由 `buildCommonRules` 统一生成。

### office_exec / shell_exec 非工作区文件操作确认

与文件工具（write_file/delete_item 等）一致，office_exec 与 shell_exec 涉及修改/删除/新建文件时，对非工作区路径弹窗确认。

**office_exec 三重防护**：
1. **执行前预扫描**（`extractWritePathsFromCode`）：用正则提取 JS 代码中**写/删上下文**的绝对路径（`file.save/append/copy/move/delete/createFolder` 的路径参数 + docx-template/pptx-template 写函数的最后一个字符串参数即 outputPath + `XLSX.writeFile` 的第二个参数 + pptxgenjs `writeFile({fileName})` 的 fileName），对非工作区路径调用 `confirmOutsideWorkspace`（统一弹窗）确认，确认后加入 `authorizedPaths` 集合
2. **异步 `file` 对象**（`createSandboxedFile`）：沙箱注入全局 `file` 对象，提供 `save/append/copy/move/delete/createFolder`（全部异步，需 await）+ `exists`（同步）。内部先 `await confirmOutsideWorkspace`（统一弹窗），确认后调用真实 fs，并追踪 writtenFiles。**沙箱 fs 移除所有写方法**（writeFileSync/writeFile 等抛错提示用 `file` 对象），只保留读方法（readFileSync/readdirSync/statSync 等）
3. **沙箱模板模块包装**（`createSandboxedTemplateModule`）：包装 docx-template/pptx-template 的写函数（createFromTemplate/renderTemplate/replaceText/setParagraphText/spliceParagraphs）为**异步函数**，内部先 `await confirmOutsideWorkspace` 确认 outputPath，再调用原始同步函数
4. **第三方库 writeFile 包装**：xlsx 的 `writeFile`/`writeFileSync` 包装为异步（内部 await 确认）；pptxgenjs 的 `writeFile({fileName})` 通过 class extends 包装为异步

**工作区目录优先级**：数字员工工作区目录（`getWorkspacePath()`）→ LLM 传入的 `working_dir` → `process.cwd()`

预扫描覆盖代码中显式出现的路径字面量；`file` 对象与模板模块包装作为运行时兜底，拦截动态构造的路径。所有弹窗统一走 `UnifiedInteractionService`（异步），不再使用 `dialog.showMessageBoxSync`（系统弹窗）。

**shell_exec 文件操作检测扩展**：
- **删除类**（fileDeletionPatterns）：rm/del/rmdir/erase/Remove-Item/rd /s/rd /q
- **写入/新建/移动/复制类**（fileWritePatterns + hasRedirection）：copy/cp/move/mv/xcopy/robocopy/Copy-Item/Move-Item/Set-Content/Add-Content/Out-File/New-Item/mkdir/md/touch/tee + 重定向 `> file`/`>> file`（排除 `2>&1` 句柄重定向）
- **路径提取**（`extractPathsFromCommand`）：提取引号包裹路径、重定向后路径、未引用绝对路径
- **确认策略**：命令为文件修改类时，提取非工作区路径逐个确认；工作区内删除保留原有命令级确认；工作区内写入/新建/移动/复制直接执行

### 文档预览（file-viewer）

智能体调用 `office_exec` 写入或生成文档后，将可预览文件回流到对话界面，用户点击卡片弹窗预览。

**数据流**（office_exec → ToolCallResult → 前端 MessageSegment）：
1. `office-exec.tool.ts` 创建 `writtenFiles: Set<string>`，通过包装 `fs` 写方法（`createSandboxedFs`）和模板模块写函数（`createSandboxedTemplateModule`）收集所有写入路径
2. handler 结束时调用 `collectGeneratedFiles(writtenFiles)`，stat 每个文件，按 `PREVIEWABLE_EXTS`（docx/xlsx/pptx/pdf/txt/md/json/xml/html/yaml/图片等）过滤，返回 `GeneratedFileInfo[]`
3. `ToolCallResult.generatedFiles` → `ToolDispatcher` → `base-agent.onToolResult` 回调 → IPC `AGENT_TOOL_RESULT` → preload → `useStreamListeners.toolResultCleanup` → `MessageSegment.generatedFiles`

**app-file:// 特权协议**（渲染进程访问本地文件）：
- `electron/main/index.ts` 通过 `protocol.registerSchemesAsPrivileged` 注册 `app-file` 协议（standard/secure/supportFetchAPI/stream/corsEnabled）
- `registerAppFileProtocol()` 使用 `protocol.handle('app-file', ...)` 读取本地文件返回流式 `Response`，处理 Windows 路径前导斜杠
- `src/utils/file-url.ts` 的 `pathToAppFileUrl()` 将绝对路径转 `app-file:///` URL

**前端组件**：
- `GeneratedFilesBar.tsx`：从 `segments` 提取所有 `tool_call` 的 `generatedFiles`，渲染卡片栏（图标+文件名+扩展名+大小），点击打开 FileViewerModal
- `FileViewerModal.tsx`：弹窗预览组件，`FileViewer` 通过 `React.lazy(() => import('@file-viewer/react-full'))` 懒加载，避免首屏加载重型依赖；浮动按钮支持重新加载（window.open）和打开文件管理器
- `MessageBubble.tsx` 在非流式输出且存在 segments 时渲染 `GeneratedFilesBar`
- 全部使用 `theme.useToken()` 适配明暗主题

**依赖与分包**：
- `@file-viewer/react-full`（Apache-2.0，v2.1.26）：纯前端文件预览组件，支持 206 个扩展名、24 条预览链路，重型渲染器按需异步加载，React 17-19 适配
- `vite.config.ts` 的 `manualChunks` 将 `@file-viewer/*` 单独拆分为 `file-viewer` chunk，避免污染主包

**多语言**：zh-CN/en-US 的 `workbench` 节新增 `previewFile`/`openInExplorer`/`reloadPreview`/`generatedFiles` 四个 key

### 性能优化

- **LRU 消息缓存**：容量 20，长任务切换时避免重复解析
- **消息窗口化**：初始展示 30 条，顶部加载更多
- **组件 memo**：CodeBlock、ThinkingSegment、ToolCallSegment、MultiChatPanel 等
- **流式渲染节流**：useDeferredValue + requestAnimationFrame
- **闭包陷阱修复**：异步回调通过 ref 读取最新 state

### 工具参数流式生成

LLM 生成工具调用参数（如 office_exec 的长文档代码）时，通过 `onToolCallDelta` 回调在流式阶段即推送增量参数给前端，避免长参数生成期间界面无响应。

**数据流**（LLM SSE delta → onToolCallDelta → IPC → 前端 segment）：
1. `openai-provider.ts` 的 `chatStream` 在累积 `delta.tool_calls` 时，每个 delta 触发 `callbacks.onToolCallDelta({ index, id?, name?, arguments })`
2. `base-agent.ts` 透传到 `AgentRunStreamCallbacks.onToolCallDelta`
3. `llm.handlers.ts` 用 `setImmediate` 批量缓冲（按 index 合并最新状态），通过 `AGENT_TOOL_CALL_DELTA` 通道发送
4. `useStreamListeners.ts` 的 `onToolCallDelta` 处理器：创建/更新 `isToolArgsStreaming: true` 的 tool_call segment，展示 `toolArgsRaw`（原始参数文本流式增长）
5. 当 `onToolCall`（最终）到达时，复用已有 streaming segment，设 `isToolArgsStreaming: false`，填入解析后的 `toolArgs`，转入"执行中"状态
6. `onDone`/`onError` 清理残留 `isToolArgsStreaming` 状态，尝试 JSON.parse `toolArgsRaw`

### KV Cache 优化

同一任务内历史消息保持不变，仅末尾追加：
- 运行时上下文（记忆/合集/技能/规划）注入系统提示词
- 工具 schema 生命周期内不变，行为通过动态引用（如 `collectionIdsRef.current`）决定
- Agent 缓存键仅含不可变配置（员工ID/供应商ID/模型ID/思考模式）

## 5.5 OCR 引擎

位于 [`electron/main/services/ocr.service.ts`](../electron/main/services/ocr.service.ts)，用于资料库中图片文件的文字识别（被 `file-parser.service.ts` 的 `parseImage()` 调用）。

**双引擎架构**，自动按可用性回退：

1. **PaddleOCR v5 mobile**（优先，ONNX 推理）
   - 依赖：`paddleocr` + `onnxruntime-node` + `sharp`
   - 模型：`resources/paddleocr/ppocr_v5_mobile/PP-OCRv5_mobile_{det,rec}_infer.onnx` + `ppocrv5_dict.txt`（Git LFS 管理）
   - 中文/英文识别精度显著优于 Tesseract，支持繁简、拼音、日文等 PP-OCRv5 单模型多语言识别
   - 字典末尾自动补 2 个空字符串占位（CTC blank/space，模型 18385 类 vs 字典 18383 行）
   - 使用 `sharp` 解码任意图片格式 → RGB 像素（PaddleOcrService 输入格式）

2. **Tesseract.js**（兜底，纯 JS WebAssembly）
   - 依赖：`tesseract.js`
   - 仅在 PaddleOCR 模型文件缺失或初始化失败时使用
   - 通用性强但中文识别能力弱

**资源路径**：[`PathService.getResourcesDir()`](../electron/main/services/path.service.ts)
- 开发模式：`<project>/resources/`
- 打包模式：`<process.resourcesPath>/resources/`（electron-builder `extraResources` 自动注入）

**打包配置**：`electron-builder.yml` 的 `extraResources` 已覆盖 `resources/`，ONNX 文件自动随安装包分发；`asarUnpack` 已覆盖 `**/*.node`，`onnxruntime-node` 的 `.node` 二进制会被解包。

## 5.6 应用日志系统

位于 [`electron/main/services/logger.ts`](../electron/main/services/logger.ts)，统一收集主进程、Worker 线程、渲染进程的 debug/info/warn/error 日志写入文件，便于 release 包排查问题。

**日志文件**：
- 路径：`{dataDir}/.log/app/app-YYYY-MM-DD-HHmmss.log`（与 LLM 日志同在 `.log` 目录下，LLM 日志在 `.log/llm/`）
- 每次主进程启动新建一个以时间命名的文件；Worker 线程复用主进程通过 `workerData.logFilePath` 传入的同一文件
- 启动时自动清理 14 天前的旧日志文件
- 用户可在设置中通过"打开日志目录"入口（`APP_OPEN_LOG_DIR`）查看

**`LoggerBackend` 单例**：
- `init(dataDir)`：主进程在启动早期调用，创建日志文件与 write stream
- `write(level, module, message, args)`：同时输出到控制台（dev 可见）与文件
- `writeToFile(level, module, message)`：仅写文件，用于渲染进程转发日志（避免主进程控制台重复打印）
- `getLogFilePath()`：供 Worker 客户端透传给子线程
- `destroy()`：应用退出时关闭 write stream

**三级日志采集**：
1. **主进程**：各服务通过 `createLogger(module)` 创建 logger，所有 `debug/info/warn/error` 调用自动写文件
2. **Worker 线程**：通过 `workerData.logFilePath` 复用主进程日志文件，`initLazy()` 在首次日志调用时自动初始化
3. **渲染进程**：[`src/utils/logger.ts`](../src/utils/logger.ts) 的 `installConsoleForwarder()` 在应用入口挂载 console 钩子，把 `console.log/info/warn/error/debug` 通过 `APP_RENDERER_LOG` IPC（fire-and-forget）转发到主进程写入文件；保留原 console 行为（devtools 仍可见）

**日志格式**：`[YYYY-MM-DD HH:mm:ss.SSS] [MODULE] [LEVEL] message args`

**已加日志的关键/易错点**：主进程启动与退出、IPC handler 错误（safeHandle）、数据库初始化与 sqlite-vec 加载、LLM API 调用失败（chat/chatStream/embedding）、OCR 引擎初始化与回退、文件解析错误、Worker 任务执行与降级、全局未捕获异常。

## 6. 开发约定

### IPC 通道

1. `electron/shared/channels/` 定义通道名和类型
2. `electron/main/ipc/` 实现 handler（使用 `safeHandle` 统一错误处理）
3. `electron/preload/index.ts` 通过 `contextBridge` 暴露 API
4. 前端通过 `window.electronAPI` 调用

### 前端约定

- UI 组件库：Ant Design 6，主题 token 替代硬编码颜色
- 状态管理：Zustand（immer 中间件）
- 国际化：`src/i18n/locales/` 维护 zh-CN / en-US
- 明暗主题：`appearance.store.ts` 管理，组件需适配

src/
  pages/             # 页面组件
