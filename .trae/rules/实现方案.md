# WorkAvatar 实现方案

> 供智能体快速了解项目架构与开发约定。

## 1. 进程模型

Electron 双进程架构：`electron/` 为主进程（Node.js），`src/` 为渲染进程（React 前端）。两者通过 `electron/preload/index.ts` 暴露的 `contextBridge` API（挂载到 `window.electronAPI`）通信，IPC 通道在 `electron/shared/channels/` 中按模块定义（app、employee、kms、llm、workspace、task、tool），对应的 handler 在 `electron/main/ipc/` 中实现。

## 2. 主进程服务清单

所有服务位于 `electron/main/services/`，均为单例模式：

- **database.service.ts** — 主数据库（better-sqlite3 + WAL 模式），管理员工、技能、工具、LLM 提供商等核心数据
- **file-parser.service.ts** — 多格式文件解析路由：PDF 使用 unpdf，DOCX/PPTX/XLSX 使用 file2md（DOCX 降级 mammoth，XLSX 降级 SheetJS），DOC 使用 word-extractor，XLS/CSV 使用 SheetJS，图片使用 OCR，TXT/MD/HTML 直接读取
- **llm-client.service.ts** — 通用 LLM 客户端，OpenAI 兼容接口，支持 SSE 流式、思考模式、向量嵌入，API Key 使用 Electron safeStorage 加密存储
- **internet-search.service.ts** — 互联网搜索：通过 Electron BrowserWindow 加载搜索引擎页面（Google/Bing/百度/DuckDuckGo），注入 JavaScript 提取搜索结果，支持多引擎自动降级切换
- **kms/** — AI原生本地资料库搜索引擎（独立模块，详见第11节，统一管理目录源与合集）
- **employee-profiling.service.ts** — 员工画像分析（基于资料库合集 + LLM，三级降级策略）
- **employee-agent.service.ts** — 员工代理服务（封装 LightAgent 调用，管理 Agent 实例缓存与工具组装）
- **employee-export.service.ts** — 员工导出入口（外观模式，统一配置导出和完整包导出）
- **employee-export-config.service.ts** — 员工配置 JSON 导出/导入（支持 skip/overwrite/merge 冲突策略）
- **employee-export-package.service.ts** — 员工完整包 .avatar 导出/导入（含 SHA-256 校验）
- **employee-memory.service.ts** — 员工跨会话记忆持久化（详见第6节）
- **skill-registry.service.ts** — Claude Skills 注册表，支持安装/卸载/分配/切换技能开关
- **task-queue.service.ts** — 后台任务队列，支持暂停/恢复/取消（AbortController 协作式取消）
- **ocr.service.ts** — OCR 文字识别（Tesseract.js + RapidOCR 降级）
- **workspace-manager.service.ts** — 员工工作区目录管理
- **path.service.ts** — 路径管理
- **unified-interaction.service.ts** — 统一交互（Agent 向用户提问/确认/选择，AsyncLocalStorage 上下文传递）
- **llm-logger.service.ts** — LLM 调用日志服务（JSONL 格式，AsyncLocalStorage 上下文传递）
- **logger.ts** — 通用日志器工厂
- **common-utils.ts** — 共享工具函数

### LightAgent 子系统

位于 `electron/main/services/agent/`，是 Agent 的核心实现：

- **core/** — Agent 基础框架：`base-agent.ts`（基类，最大迭代100次，工具超时30秒）、`agent-orchestrator.ts`（编排器，支持 sequential/parallel/supervisor 三种委派模式）、`agent-context.ts`（上下文管理）、`agent-events.ts`（事件系统，18种事件类型）、`types.ts`
- **business/** — 业务层：`employee-agent.ts`（员工代理实现，管理系统提示词的运行时上下文组件：记忆/合集/技能/规划）、`prompts.ts`（系统提示词模板，将记忆/合集/技能/规划等作为段落注入）
- **llm/** — OpenAI 兼容的 LLM Provider
- **memory/** — 记忆管理器（上下文窗口压缩，支持 sliding_window/summary/sliding_window_with_summary 三种策略，当前仅使用启发式摘要）
- **planning/** — 任务规划器（ReAct/PlanExecute/ToolFilter 三种策略）
- **tools/** — 工具层：`tool-registry.ts`（注册表）、`tool-dispatcher.ts`（分发器，支持 `ToolHandlerContext` 传递工具执行中间进度回调）、`tool-middleware.ts`（中间件链：超时/重试/日志/结果大小限制）、`types.ts`（`ToolDefinition` 接口，handler 支持可选 `ToolHandlerContext` 参数）
- **skill-manager.ts** — Claude Skills 技能管理

## 3. 工具清单

所有工具文件在 `electron/main/services/agent/tools/`：

**内置工具（20个）**：`calculator`、`date_time`、`shell_exec`（危险命令拦截）、`read_file`（支持 PDF/DOCX/XLSX/PPTX/图片OCR 等，默认最多5000字符，支持分段读取）、`write_file`（工作区外需确认，支持追加模式）、`list_dir`、`create_folder`（工作区外需确认）、`delete_item`（所有删除均需确认）、`rename_item`、`move_item`、`copy_item`、`get_file_info`、`search_files`（通配符模式）——其中文件系统操作10个工具均在 `fs-tools.ts` 中定义。另有 `system_info`、`env_vars`（仅允许安全前缀）、`web_search`（多引擎自动降级）、`web_fetch`、`json_utils`、`random_utils`、`ask_user`（confirm/select/input 三种交互）。

**Office文档工具（2个）**：`office_exec`（Node.js沙箱执行器，支持 docx/pptxgenjs/xlsx/adm-zip）、`office_guide`（Office 使用指南与代码模板）

**KMS 本地搜索工具（3个）**：`kms_search`（关键词/语义/混合检索本地文件，支持按合集过滤）、`kms_agent_search`（AI 智能检索，调用检索子智能体自主多轮检索并输出结论+溯源，支持中间过程回调通过 `ToolHandlerContext.onProgress` 实时推送到前端）、`kms_get_content`（按文件ID读取本地文件内容，支持段落/偏移/行号定位）。工具通过 `createKMSTools()` 工厂函数创建，在 `employee-agent.service.ts` 中注册到 Agent。系统提示词包含 `KMS_SEARCH_GUIDANCE` 引导数字员工在用户需要查找本地文件时优先使用这些工具

**KMS 合集管理工具（4个）**：`kms_list_collections`（列出当前会话可访问的合集）、`kms_collection_overview`（查看合集的全局摘要与文件清单）、`kms_get_toc`（获取文件的层级目录结构）、`kms_get_paragraphs`（批量获取文件段落的摘要与预览）。工具通过 `createKMSCollectionTools()` 工厂函数创建，运行时通过 `collectionIdsRef.current` 动态读取当前会话选中的合集

**工具启用控制**：`employee-agent.service.ts` 中 `getEnabledBuiltinToolIds()` 从 `employee_tools` 表读取每个员工的工具启用状态，无记录时默认全部启用。

### 文件系统工具权限管控

文件系统工具（write_file、create_folder、delete_item、rename_item、move_item、copy_item）实现了基于工作区的权限管控：工作区内操作直接执行（delete_item 除外），工作区外操作通过 UnifiedInteractionService 弹窗二次确认。

## 4. 核心数据流

### 员工创建流程

用户选择资料库合集（可选）→ EmployeeProfilingService 加载合集内容 → LLM 流式分析 → 生成员工画像和技能建议 → 用户确认 → 写入 employees 表 → 关联工具/技能 → 进入工作台。

### Agent 任务流程

用户输入 → LightAgent 初始化（加载员工配置、注册可用工具、构建系统 Prompt 含记忆/合集/技能/规划上下文、加载任务历史）→ 注入资料库检索引导 → 可选多步推理 → LLM 流式调用 → 若 LLM 返回 tool_call 则由 ToolDispatcher 执行工具并将结果加入上下文后循环回 LLM，否则直接输出最终回答 → 流式输出到前端 → 保存任务消息 → 后台异步记忆提取+过时清理+自动精炼。

### 合集任务级选择机制

数字员工与合集之间无绑定关系，合集在任务时按需选择。前端 `selectedCollectionIds` 状态 → IPC → 后端 `collectionIdsRef.current` 动态引用。KMS 合集工具始终注册，handler 在运行时读取 `collectionIdsRef.current`，无选择时工具返回提示。系统提示词包含资料库检索引导和当前可用合集信息。

## 6. 跨会话记忆系统

实现"越用越懂用户"的记忆机制：任务后 LLM 提取 → 持久化到 SQLite → 自动精炼 → 下次任务按优先级注入系统提示词。

### 数据模型

`employee_memories` 表：`id`、`employee_id`、`key`（唯一标识符）、`topic`（主题分类）、`content`、`is_pinned`、`source`（auto/manual）、`importance`（critical/normal/low）、`created_at`、`updated_at`、`last_referenced_at`

### 记忆提取

任务结束后异步调用，单次 LLM 调用同时完成记忆提取、过时检测和摘要更新：

1. 启发式预判：用户消息 <10 字符或匹配闲聊/一次性提问/临时操作等模式 → 跳过提取
2. 仅提取最后一轮任务（截断至 600 字符），从 conversations.summary 读取前文摘要
3. 读取 Top15 已有记忆（置顶+critical加权+关键词匹配+时间衰减评分）
4. LLM 调用（temperature=0.1, max_tokens=800），输出 JSON：`memories`（新记忆）、`delete_keys`（需删除）、`update_memories`（需更新）、`summary`（任务摘要 ≤500字）
5. 按 `employee_id + key` 去重合并，执行删除和更新，将 summary 写入 conversations 表

**提取策略**：聚焦用户自身特征（个人信息/行业/岗位/长期偏好/硬性禁忌/回答规则/长期计划/踩坑经验），不提取临时闲聊/一次性提问/通用知识/未变化信息。宁缺毋滥。

### 记忆精炼

当记忆数量或容量超过阈值时自动触发（1小时冷却期）：记忆数 > 50 条、总字符数 > 6400（8000×0.8）、过时记忆占比 > 30%。候选选择：≤20 条全量发送；>20 条按优先级选取 Top20。精炼操作：删除过时/无效记忆、合并语义重叠记忆、简化冗长内容、调整重要性等级。置顶记忆不可删除，超90天未引用且非置顶的记忆优先删除。

### 容量控制与注入

总字符上限 8000，条数上限 50。注入系统提示词的 `## 跨会话记忆` 段落（非用户消息），按优先级排序：置顶 > critical > normal > low > 更新时间倒序，超限时非置顶记忆按优先级截断。`conversations.summary` 存储渐进式摘要（上限 500 字），与记忆提取在同一次 LLM 调用中生成。

## 7. KV Cache 命中率优化

关键约束：**同一任务内，已发送给 LLM 的所有历史消息必须保持完全不变，仅允许在末尾追加新消息。**

- 用户消息不做修改，运行时上下文（记忆/合集/技能/规划）统一作为系统提示词段落注入
- 工具的 function schema 在 Agent 生命周期内保持不变，行为通过动态引用（如 `collectionIdsRef.current`）在运行时决定，始终发送全部注册工具
- Agent 缓存键仅包含不可变配置（员工ID、供应商ID、模型ID、思考模式）

## 8. 工作台增强功能

### 消息操作与交互

- **重新生成**：保留原始回答为分支，生成新回答
- **切换模型重新生成**：选择新模型后重新生成，保留原始回答为分支
- **编辑历史问题**：修改后自动重新生成该消息对应的助手回复，后续消息不受影响
- **分支任务**：重新生成时保留原始回答，通过左右箭头在分支间切换
- **消息删除**：删除用户消息时自动关联删除紧随其后的助手回复

### 多模型对比

MultiChatPanel 支持同时向 2-3 个不同 LLM 模型发送同一问题并排对比回答，关闭时自动聚合为分支任务。

### 思考过程与工具调用展示

- ThinkingSegment：步骤编号、思考时间、折叠/展开动画、关键推理步骤高亮
- ToolCallSegment：JSON 语法高亮、执行耗时、复制按钮、长结果截断与展开
- 工具执行进度展示：`toolProgress` 字段存储工具中间步骤，按类型 info/llm/search/read/plan/result 着色显示，仅 UI 展示不进入 LLM 上下文

### 工具执行中间进度机制

支持工具在执行过程中向前端推送中间步骤（仅展示，不进入 LLM 上下文）：

- **ToolHandlerContext**：`ToolDefinition.handler` 接受可选 `context` 参数，包含 `onProgress(progress)` 回调
- **事件链路**：工具 handler → ToolDispatcher（透传 context）→ BaseAgent.runStream（构造 context 并通过 callbacks.onToolProgress 回调）→ EmployeeAgentService.chatStream → llm.handlers.ts（通过 `AGENT_TOOL_PROGRESS` IPC 通道发送到渲染进程）→ useEmployeeChat（toolProgressCleanup 监听器将进度追加到对应 tool_call 消息段的 toolProgress 数组）→ ToolCallSegment 渲染进度时间线
- **当前应用**：`kms_agent_search` 工具使用该机制展示检索子智能体的中间步骤

### 极简模式

任务输入框下方提供"极简模式"切换：开启后所有工具不可用，系统提示词中去除工具/技能/资料库合集/工作区/记忆/规划等描述，仅保留数字员工名称、指令和身份。仅在任务无消息时可切换（切换会改变系统提示词），状态持久化在 conversations 表的 minimal_mode 字段中。

### 输入框增强

字数统计、/快捷命令（/clear、/new）、图片上传/粘贴、**文件拖拽（拖入文件后以 chip 形式展示，发送时将文件路径追加到消息内容末尾，支持 docx/pdf/txt 等任意文件类型）**、资料库合集选择（多选）、快捷命令菜单

### 消息内容展示

- 代码块：react-syntax-highlighter 语法高亮，语言标签+复制按钮，暗/亮主题适配
- LaTeX 公式：remark-math + rehype-katex
- Token 使用量：AI 消息底部显示输入/输出 Token 数，缓存命中时标注缓存量
- 消息时间分隔：两条消息间隔超过5分钟时在消息之间显示时间标签（1分钟内"刚刚"、今天"HH:mm"、昨天"昨天 HH:mm"、今年"M月D日 HH:mm"、更早"YYYY年M月D日 HH:mm"）

### 任务管理

任务列表按 `COALESCE(last_message_at, created_at) DESC` 排序。`last_message_at` 仅在用户发送/AI回复/重新生成/编辑重发时更新，非任务操作不更新。前端通过 `useMemo` 从 `allConversations` 派生排序，仅在结构性变化时重新请求后端。任务可导出为 Markdown 文件。

### 任务切换性能优化

针对长任务切换卡顿，实现"懒加载 + 内存缓存 + 让出主线程"方案：

- **LRU 消息缓存**：`useEmployeeChat` 用 `LRUCache<string, MessageWithThought[]>` 缓存已解析消息（容量上限 20），命中时先显示 spinner + `yieldToBrowser()` + 120ms 最小过渡再 setMessages
- **懒加载**：缓存未命中时立即清空 messages 并设置 loadingConversationId 渲染 Spin，IPC 拿到数据后通过两次 `yieldToBrowser()` 拆开 JSON.parse 与后处理
- **消息列表窗口化**：`visibleCount`（初始30）控制一次渲染的消息窗口，顶部"查看更早的N条消息"链接，切换任务时 `useLayoutEffect` 重置并滚到底部，加载更多时补偿 scrollTop 避免跳动

## 9. LLM 调用日志系统

所有 LLM API 交互自动记录到 JSONL 日志文件：`{dataDir}/.log/llm/{YYYY-MM-DD}/{employeeName}/{conversationId}.jsonl`。每条记录包含完整的请求和响应信息。使用 AsyncLocalStorage 传递上下文（employeeId/conversationId/source），source 标识调用来源：agent/planning/memory_extract/memory_consolidate/profiling_analyze/profiling_refine 等。

## 10. 开发约定

### 添加新 IPC 通道

1. 在 `electron/shared/channels/` 对应模块定义通道名和类型
2. 在 `electron/main/ipc/` 对应 handler 中注册处理器
3. 在 `electron/preload/index.ts` 通过 `contextBridge` 暴露 API
4. 前端通过 `window.electronAPI` 调用

### 添加新服务

1. 在 `electron/main/services/` 下创建单例服务类
2. 在对应 IPC handler 中注册该服务的 IPC 通道
3. 在 preload 脚本中暴露对应 API

### 添加新页面

1. 在 `src/pages/` 下创建页面组件
2. 在 `src/router/index.tsx` 添加路由
3. 在 `src/App.tsx` 侧边栏添加导航入口

### 技术约束

- UI 组件库：Ant Design 6，注意废弃属性
- 前端状态管理：Zustand（immer 中间件）
- 国际化：`src/i18n/locales/` 中维护 `zh-CN.ts` 和 `en-US.ts`，使用 `useTranslation` hook
- 主题：通过 `appearance.store.ts` 管理暗/亮切换，所有组件需适配
- 构建：`npm run dev` 启动开发，`npm run build` / `.\build.ps1` 生产构建（Windows）
- 构建配置中 `signAndEditExecutable: false` 跳过了 winCodeSign 下载阶段，因为当前打包不需要代码签名（无证书），跳过该阶段可避免 macOS 符号链接导致的 7za 提取报错与缓存失效问题。`BrowserWindow.icon` 在运行时设置，exe 文件图标不嵌入。

## 11. KMS 本地资料库搜索引擎

独立模块，位于 `electron/main/services/kms/`，使用独立 SQLite 数据库（`workavatar-kms.db`）。统一管理两类资料来源：**目录源**（自动跟踪本地目录的文件变更）和**合集**（手动挑选文件组成的稳定资料集）。定位为既能独立当桌面搜索工具用，也能作为检索组件接入各类AI智能体。

### 子服务

- **kms-database.service.ts** — KMS独立数据库（索引目录、文件注册表、FTS5索引、向量嵌入、冷热数据、访问追踪、合集与合集摘要）
- **kms-crawler.service.ts** — 目录爬虫（扫描索引目录、检测文件变更、增量索引、访问统计）
- **kms-search-engine.service.ts** — 核心搜索引擎（FTS5全文检索+向量语义+混合搜索+时间范围过滤+文件扩展名过滤）。向量检索优先用 sqlite-vec 的 vec0 虚表 KNN 索引（metadata=file_id/source_type，无 partition key 全局搜索），维度不匹配或扩展不可用时回退到 JS 全扫描
- **kms-index-manager.service.ts** — 索引管理器（全量/增量/重建索引、向量嵌入生成、冷热数据晋升/降级）。`buildFullIndex`/`incrementalIndex`/`rebuildDirIndex` 均接受 `withEmbedding` 参数（默认 true），true 时同步生成向量嵌入，false 时仅构建全文索引；`generateEmbeddings(forceRegenerate?)` 支持强制清空 `kms_embeddings` 表后重建
- **kms-search-agent.service.ts** — 独立检索子智能体（LLM驱动的查询分类、检索路径规划、多轮检索、结果提纯）
- **kms-mcp.service.ts** — KMS MCP 服务（Streamable HTTP 传输，11个检索与合集工具暴露给第三方智能体：kms_list_dirs/kms_stats/kms_search/kms_agent_search/kms_get_content/kms_get_summary/kms_list_collections/kms_list_files_in_collection/kms_get_collection_summary/kms_get_toc/kms_get_paragraphs）
- **kms.service.ts** — 顶层外观服务（组合爬虫/搜索引擎/索引管理器/检索子智能体，提供统一API）

### 冷热数据机制

- **冷数据**：索引文件名和关键词，生成轻量摘要（文件名+文件开头500字符，不调用LLM），海量文档可快速上线
- **热数据**：额外生成LLM摘要（150字+5-8关键词+3-5主题）和段落索引，支持深度语义检索
- **目录摘要**：每个索引目录生成目录级摘要，帮助检索子智能体判断哪些目录/文件可能相关
- **手动生成摘要**：知识沉淀视图提供手动生成入口，`generateDirSummaryManual(dirId)` 重新生成指定目录摘要，`generateFileSummaryManual(fileId)` 对单个文件执行深度处理（段落切分/TOC/段落摘要/文件摘要）并生成向量嵌入，无需运行全量索引
- **晋升条件**：30天内搜索命中≥5次或读取≥3次 → 冷→热
- **降级条件**：90天无访问 → 热→冷

### 独立检索子智能体

`kms-search-agent.service.ts` 实现内部闭环的检索流程，最终只输出核心结论加精准溯源信息，不挤占主智能体上下文：

1. **查询类型识别**：LLM 自动识别四类需求 → locate（定位查找）/ concept（概念解释）/ trend（趋势梳理）/ analysis（综合分析），LLM不可用时正则降级
2. **获取文件清单**：从数据库获取索引目录的文件名、路径、轻量摘要（最多200个文件），为LLM规划提供上下文
3. **检索路径规划**：LLM 结合文件清单和目录摘要，生成1-3组关键词查询+候选文件ID
4. **多轮检索执行**：按规划自主执行多轮检索，每轮基于前一轮结果补充查找，结果达到topK*2时提前结束
5. **信息补充**：不足时读取最多5个文件片段（每个2000字符）补充信息
6. **结果提纯**：LLM 对搜索结果+补充读取内容进行筛选、去重、提纯，生成结论（≤500字）+ 精准溯源（文件路径、页码、行号、偏移量）
7. **降级策略**：LLM 不可用时降级为单次混合检索 + 关键词摘要

**中间过程输出**：检索过程通过 `onProgress` 回调实时推送结构化步骤（`SearchTraceStep`），前端实时展示检索进度时间线。

### KMS MCP 服务

`kms-mcp.service.ts` 将本地检索能力暴露为 MCP 服务，供 Claude Code、Cursor 等主流智能体及自定义 Agent 工作流接入：

- **传输协议**：MCP Streamable HTTP（POST /mcp），兼容 2025-03-26 协议版本
- **暴露工具（8个）**：`kms_list_sources`（列出资料来源：目录源与合集）、`kms_stats`（查看索引统计）、`kms_search`（关键词/语义/混合检索）、`kms_agent_search`（AI检索子智能体，核心）、`kms_get_content`（获取文件内容，支持段落ID/偏移/行号定位）、`kms_get_summary`（获取文件摘要，仅热数据可用）、`kms_get_toc`（获取文件层级目录结构）、`kms_get_paragraphs`（批量获取文件段落摘要与预览）
- **配置项**：启用/禁用、端口号（默认3101）、API Key 身份验证
- **设置页面**：全局设置中"本地搜索 MCP"标签页

### 合集管理

合集是手动挑选文件组成的稳定资料集，与目录源（自动跟踪）互补。合集文件默认注册到 `__manual_files__` 虚拟目录（`enabled=0`，不参与目录扫描），相同内容文件按 `file_hash` 去重并复用索引。

- **AI 摘要生成**：`generateCollectionSummary(collectionId)` 收集合集内所有文件的摘要（最多 12000 字符），调用 LLM 生成全局摘要与关键主题，写入 `kms_collection_summaries` 表。模型选择优先级：KMS 专属设置 > 知识场景默认模型 > 任意可用提供商
- **目录批量扫描**：`scanDirFiles(dirPath, extensions?)` 递归扫描本地目录收集支持的文件路径（PDF/Word/Excel/PPT/Markdown/TXT 等），用于合集的文件夹批量导入
- **文件变更自动索引**：`addFileToCollection` 通过 `modified_time` 与 `file_hash` 比对检测文件变更，新增或变更的 pending 文件会异步触发 `incrementalIndex()`（fire-and-forget），无需用户手动重建索引

### 合集深度处理

合集深度处理（`processCollectionDeep`）是对合集内所有文件做一次性全流程深度处理的入口，使合集具备完整的章节检索、段落摘要、文件摘要与合集摘要能力，能力对标原知识库功能并融入知识沉淀体系。与全量/增量索引不同，本流程不依赖冷热数据机制，强制对所有文件做深度处理。

**处理流程**（在 `kms-index-manager.service.ts` 中实现，`processHotFile` 方法为核心，对齐旧知识库 `KnowledgeProcessorService` 的处理流程，通过 `kms.service.ts` 的公共包装器触发，进度通过 `KMS_INDEX_PROGRESS` 通道推送，含 `collectionId`/`collectionName` 字段便于按合集过滤）：

1. **文件解析与索引**（`parsing` 阶段）：解析文件全文 → 清除旧索引 → 建立文件名与内容段落索引 → 保存轻量摘要
2. **段落识别**（`paragraph_split` 阶段，`splitParagraphs` 方法）：对齐旧知识库 `identifyParagraphs` 逻辑。第一遍扫描 `detectHeading()` 识别所有标题行（支持 Markdown `#`/`##`/`###`、`第X章`/`第X节`、数字编号 `1.`/`1.1`/`1.1.1`、中文数字 `一、`、中文括号 `（一）` 等多种模式；过滤末尾标点 `。！？；` 与超长行避免误判），然后按偏移量切分：无标题或标题密度超 25% → 降级为固定大小分块（5000字符/500重叠）；首个标题前的内容作为"前言"段落；超长段落按 5000 字符二次切分（500重叠）。
3. **LLM 目录恢复**（`toc` 阶段，`restoreTocWithLLM` 方法）：对齐旧知识库 `restoreTocWithLLM`。当文档缺少明显标题结构时（无标题或平均每标题承载超 8000 字符），调用 LLM 逐块分析章节结构，验证后在原文中匹配行号与偏移量，基于 LLM 还原的 TOC 重新切分段落。LLM 不可用时回退到正则切分结果。
4. **目录章节生成**（`toc` 阶段，`generateFileToc` 方法）：从段落标题派生层级目录结构，写入 `kms_file_summaries.toc_json`（LLM TOC 恢复时优先使用 LLM 还原的目录）
5. **段落摘要生成**（`paragraph_summary` 阶段，`generateParagraphSummary` 方法）：对齐旧知识库，逐段调用 LLM 生成段落级摘要（50字以内）+ 3-5 关键词，仅对内容词数 ≥ 50 的段落生成。生成后通过 `updateParagraphSummaries` 批量写入数据库和搜索索引
6. **文件摘要生成**（`doc_summary` 阶段，`generateDocumentSummaryFromParagraphs` 方法）：对齐旧知识库 `generateDocumentSummary`，基于段落摘要汇总生成（非直接基于全文），150 字全局摘要 + 5-8 关键词 + 3-5 主题。无段落摘要时降级为基于全文生成（`generateFileSummary`）
7. **段落向量化**（`embedding` 阶段）：复用 `generateEmbeddings` 生成段落向量嵌入
8. **合集摘要生成**（`collection_summary` 阶段）：调用 `generateCollectionSummary` 生成合集级 LLM 摘要
9. **合集摘要向量化**（`collection_embedding` 阶段）：将合集摘要文本转为向量嵌入，直接写入 `kms_collection_summaries.embedding`/`dimension`/`embedding_model` 字段（避免破坏 `kms_embeddings` 表的 `file_id` 外键约束）

**进度可视化**（`KMSCollectionProcessModal.tsx`）：合集卡片新增"深度处理"按钮（ThunderboltOutlined 图标），点击后弹出进度弹窗，订阅 `onIndexProgress` 按 `collectionId` 过滤展示：

- 总体进度条（按9阶段加权计算百分比）+ 耗时计时
- 当前文件高亮卡片（文件名、X/总数）
- 9 阶段时间线（pending/processing/done 三态，含子进度条与消息）
- 错误提示卡片（含错误详情）
- footer 双按钮：**后台运行**（关闭弹窗但保留后台处理）+ **取消处理**（调用 `cancelCollectionDeepProcess` 终止后台任务）；完成后变为"关闭"按钮
- 弹窗始终可关闭（`closable=true`），不阻塞主窗口，用户可在后台处理期间继续使用智能体等功能
- 取消时弹窗展示"已取消"标题与提示卡片，已处理的文件保留

**后台处理状态跟踪**（`KMSCollectionsView.tsx`）：弹窗关闭后通过全局 `onIndexProgress` 订阅持续跟踪带 `collectionId` 的进度事件，维护 `processingMap` 状态：

- 合集列表上方渲染浮动 `Alert` 指示器，显示每个后台处理中的合集名称、总体百分比、当前消息，并提供"查看进度"按钮重新打开进度弹窗
- 合集卡片"深度处理"按钮在处理中自动切换为 `LoadingOutlined` 图标，tooltip 变为"查看进度"，点击重新打开弹窗（不触发新处理）
- 完成/错误事件触发后自动从 `processingMap` 移除并刷新合集列表与摘要

**降级与取消**：LLM 不可用时返回 `NO_LLM_PROVIDER` 错误；用户可随时取消（`AbortController`），取消后返回 `ABORTED`。后端在所有 abort 检查点会发出 `done` 进度事件（消息含"已取消"标记），避免前端因等待结束事件而卡死；`generateCollectionSummary(collectionId, signal?)` 透传 signal 给 `llmClient.chat()`，确保合集摘要 LLM 调用阶段也可被中断。

### 文件段落增量重新生成

支持对已深度处理的合集文件，从指定段落节点开始重新生成后续内容，避免每次全量重处理。

**入口**（`KMSCollectionsView.tsx` 合集详情抽屉 → 文件展开行 → 段落 Tree 节点）：每个 Tree 节点 hover 时显示"从此节点重新生成"按钮（`RetweetOutlined` 图标 + `Popconfirm` 二次确认），确认后触发 `regenerateFileParagraph(fileId, paragraphId)`。

**后端处理**（`kms-index-manager.service.ts` 的 `regenerateFileParagraph(fileId, fromParagraphId, onProgress?)`）：

1. 读取目标段落信息（`paragraphIndex`、`startOffset`），保留该段落之前的所有段落不变
2. 调用 `searchEngine.deleteParagraphsFromFileIndex(fileId, fromIndex)` 删除该段落及之后的所有段落、FTS 索引、向量嵌入
3. 从 `fromStartOffset` 重新切分剩余文本（`splitParagraphs`），新段落的 `paragraphIndex` 从 `fromIndex` 起递增、`startOffset`/`endOffset` 加上 `fromStartOffset` 偏移
4. 调用 `searchEngine.insertParagraphs`（增量插入，不清除已有段落）写入新段落
5. 从全部段落（保留 + 新增）刷新 TOC 写入 `kms_file_summaries.toc_json`
6. 对新段落执行索引、批量摘要、文件摘要、向量嵌入
7. 全程透传 `AbortSignal`，复用 `this.abortController`，可被 `cancelFileParagraphRegenerate()` 中断

**进度跟踪**：进度事件通过 `KMS_INDEX_PROGRESS` 推送，携带 `fileId`/`fileName` 但 **不带 `collectionId`**，前端据此区分文件级重新生成与合集深度处理。`KMSCollectionsView.tsx` 在抽屉顶部渲染 `Alert` + `Progress` 条显示当前阶段、消息、百分比，并提供取消按钮；完成/错误事件触发后清除 `regenerateState` 并通过 `loadFileDetailRef` 刷新该文件详情缓存与 Tree 展示。

**新增 IPC 通道**：

- `KMS_REGENERATE_FILE_PARAGRAPH`（`kms:regenerate-file-paragraph`）：fire-and-forget 触发重新生成
- `KMS_CANCEL_REGENERATE_FILE_PARAGRAPH`（`kms:cancel-regenerate-file-paragraph`）：取消进行中的重新生成

**新增 SearchEngine 方法**（`kms-search-engine.service.ts`）：

- `deleteParagraphsFromFileIndex(fileId, fromIndex)`：删除指定 `paragraph_index >= fromIndex` 的段落及其 FTS、向量嵌入
- `insertParagraphs(fileId, paragraphs)`：增量插入段落（不删除已有，区别于 `saveParagraphs` 的全量替换）
- `getMaxParagraphIndex(fileId)`：返回文件当前最大段落索引，用于增量插入时续号

### KMS 设置面板

`KMSSettingsPanel.tsx` 采用分 Tab 结构（抽屉式）：

- **模型设置 Tab**：配置 KMS 专属的 AI 搜索模型和向量嵌入模型（使用 LLMSelector 组件），并配置 **Embedding 最大字符数**（settings 表 `embedding_max_chars` 键，100-32000，控制每次 Embedding 计算的字符上限，已从全局默认模型设置迁移至此）
- **检索参数 Tab**：调整 AI 检索的最大轮次（1-5）和每轮结果数量（3-30）
- **索引目录 Tab**：管理需要建立索引的本地目录
- **索引管理 Tab**：管理索引构建、增量更新、重建，内含自动索引配置。"全量构建"/"增量更新"/"重建索引"按钮旁提供"同时构建智能索引"开关（`withEmbedding`，默认开启），开启时索引构建完成会同步生成向量嵌入以支持语义检索，关闭时仅构建全文索引（速度更快）。统计信息卡片已移除（迁移至"知识沉淀视图 - 统计信息 Tab"）

**模型优先级**：AI 检索时模型选择优先级为 KMS 专属设置 > 知识场景默认模型 > 任意可用提供商。向量嵌入阶段独立解析 Embedding 提供商（KMS Embedding 配置 > 默认 Embedding 配置），与对话/摘要使用的 chat providerId 解耦，确保即使未配置对话模型也能正常生成向量索引。**未配置 Embedding 模型时**，`generateEmbeddings` 不再静默跳过，而是通过 `onProgress` 推送 `phase: 'error'` 事件并提示"未配置 Embedding 模型，请在「设置 - 模型设置」中配置智能索引模型后重试"；所有待嵌入条目已处理完毕时推送 `phase: 'embedding'` 提示进度，避免用户感知不到反馈。

### 自动索引

索引管理 Tab 中提供自动索引配置，实现文件变更的自动检测和增量重建：

- **配置项**（存储在主数据库 `settings` 表的 `kms_auto_index` 键）：`enabled`（是否启用）、`intervalMinutes`（检查间隔1-1440分钟，默认10）、`stableThresholdSeconds`（文件稳定阈值0-86400秒，默认300=5分钟）
- **工作流程**：应用启动时读取配置→`setInterval`启动定时器→带稳定阈值扫描所有启用索引目录→检测到变更后增量解析和索引→通过 `KMS_INDEX_PROGRESS` 事件通道推送进度。自动索引与手动索引互斥
- **文件稳定阈值**：修改的文件在最后修改时间距今不足阈值时跳过，避免编辑中频繁触发。新增和删除的文件不受阈值影响

### IPC通道

54个通道，定义在 `electron/shared/channels/kms.ts`，handler 在 `electron/main/ipc/kms.handlers.ts`，preload API 挂载在 `window.electronAPI.kms`（检索能力+设置+知识沉淀+搜索历史+自动索引+合集管理+AI摘要生成+目录扫描+合集深度处理+手动生成目录摘要+手动生成文件摘要）和 `window.electronAPI.kmsMcp`（MCP 服务管理）。合集深度处理的进度事件复用 `KMS_INDEX_PROGRESS` 通道推送（携带 `collectionId`/`collectionName` 字段，便于前端按合集过滤）。
