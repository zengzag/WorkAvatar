# WorkAvatar 实现方案

> 供智能体快速了解项目架构与开发约定。用文字表述，避免图形和长目录树。

## 1. 进程模型

Electron 双进程架构：`electron/` 为主进程（Node.js），`src/` 为渲染进程（React 前端）。两者通过 `electron/preload/index.ts` 暴露的 `contextBridge` API（挂载到 `window.electronAPI`）通信，IPC 通道在 `electron/shared/channels/` 中按模块定义（app、employee、kb、kb-mcp、kms、llm、workspace、task、tool），对应的 handler 在 `electron/main/ipc/` 中实现。

## 2. 主进程服务清单

所有服务位于 `electron/main/services/`，均为单例模式：

- **database.service.ts** — 主数据库（better-sqlite3 + WAL 模式），管理员工、技能、工具、LLM 提供商等核心数据
- **kb-database.service.ts** — 知识库专用数据库（独立 SQLite 实例），管理知识库、文档、段落、摘要、向量嵌入等
- **file-parser.service.ts** — 多格式文件解析路由：PDF 使用 unpdf，DOCX/PPTX/XLSX 使用 file2md（DOCX 降级 mammoth，XLSX 降级 SheetJS），DOC 使用 word-extractor，XLS/CSV 使用 SheetJS，图片使用 OCR，TXT/MD/HTML 直接读取
- **llm-client.service.ts** — 通用 LLM 客户端，OpenAI 兼容接口，支持 SSE 流式、思考模式、向量嵌入，API Key 使用 Electron safeStorage 加密存储
- **knowledge-processor.service.ts** — 知识处理流水线：解析阶段完成段落切分（含标题层级路径 titlePath，目录优先分段+长段落自动切分，首个标题前的正文作为"前言"段落保留）和目录提取（从 Markdown 标题提取，最多3级目录）；知识处理阶段先通过 LLM 还原丢失的目录结构（PDF/Word 转换后标题标记丢失时自动触发），再生成摘要（段落摘要和文档摘要均限制150字以内）
- **search-engine.service.ts** — 搜索引擎：FTS5 全文检索 + Embedding 向量语义搜索 + 混合搜索（BM25+余弦相似度加权），LRU 缓存
- **internet-search.service.ts** — 互联网搜索：通过 Electron BrowserWindow 加载搜索引擎页面（Google/Bing/百度/DuckDuckGo），注入 JavaScript 提取搜索结果，支持多引擎自动降级切换
- **kms/** — AI原生本地知识库搜索引擎（独立模块，详见第11节）
- **kb.service.ts** — 知识库顶层服务（外观模式，组合文档/段落/摘要/导出四个子服务）
- **kb-document.service.ts** — 知识库文档管理
- **kb-paragraph.service.ts** — 段落管理
- **kb-summary.service.ts** — 摘要管理
- **kb-export.service.ts** — 知识库导入导出
- **kb-mcp.service.ts** — 知识库 MCP 服务（MCP Streamable HTTP 传输协议，将6个知识库工具暴露为 MCP 工具供第三方智能体调用，支持端口配置、API Key 身份验证、知识库访问控制）
- **employee-profiling.service.ts** — 员工画像分析（基于知识库 + LLM，三级降级策略）
- **employee-agent.service.ts** — 员工代理服务（封装 LightAgent 调用，管理 Agent 实例缓存与工具组装）
- **employee-export.service.ts** — 员工导出入口（外观模式，统一配置导出和完整包导出）
- **employee-export-config.service.ts** — 员工配置 JSON 导出/导入（支持 skip/overwrite/merge 冲突策略）
- **employee-export-package.service.ts** — 员工完整包 .avatar 导出/导入（含 SHA-256 校验）
- **employee-memory.service.ts** — 员工跨会话记忆持久化（详见第6节）
- **skill-registry.service.ts** — Claude Skills 注册表，支持安装/卸载/分配/切换技能开关
- **tool-engine.service.ts** — 旧版工具引擎（Agent 子系统有独立的工具框架）
- **task-queue.service.ts** — 后台任务队列，支持暂停/恢复/取消（AbortController 协作式取消）
- **parse-task-manager.service.ts** — 解析任务管理
- **ocr.service.ts** — OCR 文字识别（Tesseract.js + RapidOCR 降级）
- **workspace-manager.service.ts** — 员工工作区目录管理
- **path.service.ts** — 路径管理
- **unified-interaction.service.ts** — 统一交互（Agent 向用户提问/确认/选择，AsyncLocalStorage 上下文传递）
- **llm-logger.service.ts** — LLM 调用日志服务（JSONL 格式，AsyncLocalStorage 上下文传递）
- **logger.ts** — 通用日志器工厂
- **common-utils.ts** — 共享工具函数

### LightAgent 子系统

位于 `electron/main/services/agent/`，是 Agent 的核心实现：

- **core/** — Agent 基础框架：`base-agent.ts`（基类，最大迭代100次，工具超时30秒）、`agent-orchestrator.ts`（编排器，支持 sequential/parallel/supervisor 三种委派模式）、`agent-context.ts`（上下文管理）、`agent-events.ts`（事件系统，18种事件类型）
- **business/** — 业务层：`employee-agent.ts`（员工代理实现，管理系统提示词的运行时上下文组件：记忆/KB/技能/规划）、`prompts.ts`（系统提示词模板，将记忆/KB/技能/规划等作为段落注入）
- **llm/** — OpenAI 兼容的 LLM Provider
- **memory/** — 记忆管理器（上下文窗口压缩，支持 sliding_window/summary/sliding_window_with_summary 三种策略，当前仅使用启发式摘要）
- **planning/** — 任务规划器（ReAct/PlanExecute/ToolFilter 三种策略）
- **tools/** — 工具层：`tool-registry.ts`（注册表）、`tool-dispatcher.ts`（分发器）、`tool-middleware.ts`（中间件链：超时/重试/日志/结果大小限制）
- **skill-manager.ts** — Claude Skills 技能管理

## 3. 工具清单

所有工具文件在 `electron/main/services/agent/tools/`：

**内置工具（20个）**：`calculator`、`date_time`、`shell_exec`（危险命令拦截，文件删除需确认）、`read_file`（支持 PDF/DOCX/XLSX/PPTX/图片OCR 等，默认最多返回 5000 字符，支持分段读取）、`write_file`（工作区外需确认，支持追加模式）、`list_dir`（结构化输出，含大小和修改时间）、`create_folder`（工作区外需确认）、`delete_item`（所有删除均需用户确认）、`rename_item`（工作区外需确认，防路径遍历）、`move_item`（工作区外需确认）、`copy_item`（工作区外需确认）、`get_file_info`（文件/文件夹详细信息）、`search_files`（通配符模式搜索文件名）、`system_info`、`env_vars`（仅允许安全前缀）、`web_search`（多引擎自动降级）、`web_fetch`、`json_utils`、`random_utils`、`ask_user`（confirm/select/input 三种交互）

**Office文档工具（2个）**：`office_exec`（Node.js沙箱执行器，支持 docx/pptxgenjs/xlsx/adm-zip）、`office_guide`（Office 使用指南与代码模板）

**知识库查询工具（6个）**：`kb_list`、`kb_overview`、`kb_get_toc`、`kb_get_paragraphs`、`kb_search`（混合搜索，支持按来源类型筛选）、`kb_get_content`（支持段落ID/段落ID数组/字符偏移/行号定位，paragraph_ids数组可批量获取多段完整内容）。工具返回内容采用紧凑格式以节省token

此外还支持 Claude Skills 工具动态注入。

### 文件系统工具权限管控

文件系统工具（write_file、create_folder、delete_item、rename_item、move_item、copy_item）实现了基于工作区的权限管控：
- **工作区内操作**：直接执行，无需确认（delete_item 除外，所有删除操作均需确认）
- **工作区外操作**：通过 UnifiedInteractionService 弹窗二次确认，用户可取消
- **路径判断**：通过 `interactionContext` 获取当前员工 ID，查询 `employees.workspace_path` 判断路径是否在工作区内

### 知识库 MCP 服务

`kb-mcp.service.ts` 将上述6个知识库查询工具封装为 MCP (Model Context Protocol) 服务，供第三方智能体通过 HTTP 调用：

- **传输协议**：MCP Streamable HTTP（POST /mcp），兼容 2025-03-26 协议版本
- **工具暴露**：6个知识库工具（kb_list、kb_overview、kb_get_toc、kb_get_paragraphs、kb_search、kb_get_content）
- **访问控制**：支持配置允许访问的知识库列表（空=全部），支持 API Key 身份验证
- **配置项**：启用/禁用、端口号（默认3100）、允许的知识库ID列表、API Key
- **设置页面**：全局设置中"知识库 MCP"标签页，控制服务启停和参数配置

## 4. 核心数据流

### 员工创建流程

用户选择知识库（可选）→ EmployeeProfilingService 加载知识库内容 → LLM 流式分析 → 生成员工画像和技能建议 → 用户确认 → 写入 employees 表 → 关联工具/技能 → 进入工作台。

### Agent 对话流程

用户输入 → LightAgent 初始化（加载员工配置、注册可用工具、构建系统 Prompt 含记忆/KB/技能/规划上下文、加载对话历史）→ 若对话选择了知识库则注册知识库查询工具并注入知识库检索引导 → 可选多步推理 → LLM 流式调用 → 若 LLM 返回 tool_call 则由 ToolDispatcher 执行工具并将结果加入上下文后循环回 LLM，否则直接输出最终回答 → 流式输出到前端 → 保存对话消息 → 后台异步记忆提取+过时清理+自动精炼。

### 知识库对话级选择机制

- 数字员工与知识库之间无绑定关系，知识库在对话时按需选择
- 前端 `selectedKbIds` 状态 → IPC → 后端 `kbIdsRef.current` 动态引用
- KB 工具始终注册，handler 在运行时读取 `kbIdsRef.current`，无选择时工具返回提示
- 系统提示词包含知识库检索引导和当前可用知识库信息

## 6. 跨会话记忆系统

实现"越用越懂用户"的记忆机制，核心流程：对话后 LLM 提取 → 持久化到 SQLite → 自动精炼 → 下次对话按优先级注入系统提示词。

### 数据模型

`employee_memories` 表：`id`、`employee_id`、`key`（唯一标识符）、`topic`（主题分类）、`content`、`is_pinned`、`source`（auto/manual）、`importance`（critical/normal/low）、`created_at`、`updated_at`、`last_referenced_at`

### 记忆提取

对话结束后异步调用（fire-and-forget），单次 LLM 调用同时完成记忆提取、过时检测和摘要更新：

1. 启发式预判：用户消息 <10 字符或匹配闲聊/一次性提问/临时操作等模式 → 跳过提取
2. 仅提取最后一轮对话（截断至 600 字符），从 conversations.summary 读取前文摘要
3. 读取相关性最高的 Top15 已有记忆（置顶+critical加权+关键词匹配+时间衰减评分）
4. LLM 调用（temperature=0.1, max_tokens=800），输出 JSON：`memories`（新记忆）、`delete_keys`（需删除）、`update_memories`（需更新）、`summary`（对话摘要 ≤500字）
5. 按 `employee_id + key` 去重合并，执行删除和更新，将 summary 写入 conversations 表

**提取策略**：聚焦用户自身特征而非临时业务细节。需提取：①用户个人信息/行业/岗位/常用办公工具 ②长期偏好（写作风格/文档格式/汇报偏好/沟通风格等办公场景偏好） ③硬性禁忌/约束 ④用户自定义回答规则（格式/语气/风格） ⑤确认落地的长期计划/关键方案 ⑥踩坑经验（办公工具/流程失败原因及解决方案）。不提取：临时闲聊、一次性临时提问、随口临时想法、临时业务细节、通用知识、已存在且未变化的信息。宁缺毋滥，允许返回空结果不提取任何信息。

### 记忆精炼

当记忆数量或容量超过阈值时自动触发 LLM 驱动的精炼（1小时冷却期）：

- **触发条件**：记忆数 > 50 条、总字符数 > 6400（8000×0.8）、过时记忆占比 > 30%
- **候选选择**：≤20 条全量发送；>20 条按优先级选取 Top20（置顶+近期+最旧）
- **精炼操作**：删除过时/无效记忆、合并语义重叠记忆、简化冗长内容、调整重要性等级
- **精炼规则**：置顶记忆不删除（可合并/简化）、手动添加记忆谨慎删除、超90天未引用且非置顶记忆优先删除、优先保留用户自身特征/偏好/踩坑经验，清理纯临时业务细节

### 过时记忆清理

`removeStaleMemories`：直接删除满足全部条件的记忆：非置顶 + importance=low + 超过90天未引用

### 记忆容量控制

- 总字符上限 8000（`MEMORY_MAX_CHARS`），记忆条数上限 50（`MEMORY_MAX_COUNT`）
- 注入时按优先级排序：置顶 > critical > normal > low > 更新时间倒序
- 超过字符上限时，非置顶记忆按优先级截断

### 记忆注入

记忆内容注入系统提示词的 `## 跨会话记忆（关于该用户的持久信息）` 段落，而非拼接到用户查询中，确保同一对话内历史消息前缀不变以保障 KV Cache 命中。

### 对话摘要

`conversations.summary` 存储渐进式摘要（上限 500 字），与记忆提取在同一次 LLM 调用中生成，不单独消耗 token。

### 记忆管理 UI

员工设置页"记忆"标签页：记忆开关、容量进度条、统计标签、精炼按钮、查看/搜索/删除/置顶/编辑记忆条目、手动添加（含重要性选择）。

## 7. KV Cache 命中率优化

LLM 提供商对请求前缀进行 KV cache，相同前缀可复用缓存避免重复计算。关键约束：**同一对话内，已发送给 LLM 的所有历史消息必须保持完全不变，仅允许在末尾追加新消息。** 跨对话之间无需保证 KV Cache 命中。

- **用户消息不做修改**：用户消息始终保持原始内容，不拼接任何前缀
- **运行时上下文统一注入系统提示词**：记忆、知识库上下文、已激活技能指令、工具规划建议等所有运行时上下文统一作为系统提示词的段落注入，而非拼接到用户查询中
- **工具定义稳定**：工具的 OpenAI function schema 在 Agent 生命周期内保持不变。工具行为通过动态引用（如 `kbIdsRef.current`）在运行时决定。工具描述使用通用文案，不嵌入具体 ID 或名称。始终发送全部注册工具
- **Agent 缓存键不含运行时状态**：缓存键仅包含不可变配置（员工ID、供应商ID、模型ID、思考模式），不包含运行时可能变化的参数

## 8. 工作台增强功能

### 消息操作与交互

- **重新生成**：保留原始回答为分支，生成新回答
- **切换模型重新生成**：选择新模型后重新生成，同样保留原始回答为分支
- **编辑历史问题**：修改后自动重新生成该消息对应的助手回复（原回复保留为分支），后续消息不受影响；上下文仅使用被编辑消息及其上方的消息
- **分支对话**：重新生成时保留原始回答，通过左右箭头在分支间切换
- **消息删除**：删除用户消息时自动关联删除紧随其后的助手回复

### 多模型对比

MultiChatPanel 支持同时向 2-3 个不同 LLM 模型发送同一问题并排对比回答，关闭时自动聚合为分支对话。

### 思考过程与工具调用展示

- ThinkingSegment：步骤编号、思考时间、折叠/展开动画、关键推理步骤高亮
- ToolCallSegment：JSON 语法高亮、执行耗时、复制按钮、长结果截断与展开

### 输入框增强

字数统计、/快捷命令（/clear、/new）、图片上传/粘贴、知识库选择（多选）、快捷命令菜单

### 极简模式

对话输入框下方提供"极简模式"状态切换按钮（Switch + 文字标签），控制对话是否启用极简模式：

- **默认关闭**：关闭时功能与普通模式完全一致
- **开启效果**：所有工具不可用（系统工具、文件系统工具、知识库工具、技能工具等），LLM 调用时不传 tools 信息；系统提示词中去除工具、技能、知识库、工作区、记忆、规划等相关描述，仅保留数字员工名称、指令和身份
- **切换限制**：仅在对话无任何消息时可切换（因为切换会改变系统提示词，有对话时不允许切换以保持历史提示词不变）
- **状态持久化**：极简模式状态保存在 conversations 表的 minimal_mode 字段中，切换对话时自动还原显示

### 消息内容展示

- 代码块：react-syntax-highlighter 语法高亮，语言标签+复制按钮，暗/亮主题适配
- LaTeX 公式：remark-math + rehype-katex
- Token 使用量：AI 消息底部显示输入/输出 Token 数，缓存命中时标注缓存量，多轮工具调用累加计算
- 消息时间分隔：两条消息间隔超过5分钟时在消息之间显示时间标签，首条消息始终显示时间。时间格式按主流聊天软件规则：1分钟内显示"刚刚"、今天显示"HH:mm"、昨天显示"昨天 HH:mm"、今年显示"M月D日 HH:mm"、更早显示"YYYY年M月D日 HH:mm"（英文环境对应格式）。时间标签居中显示，使用辅助色小字号

### 对话列表排序

对话列表按 `COALESCE(last_message_at, created_at) DESC` 排序（最后有消息的对话排最前）。`last_message_at` 是专门记录最后对话时间的字段，仅在以下操作时更新：用户发送消息、AI 回复完成、重新生成、编辑重发。选择对话、修改标题等操作不会更新 `last_message_at`，确保列表不会因非对话操作而跳动。新对话的 `last_message_at` 为 NULL，此时回退到 `created_at` 排序。

**双层排序策略**：
- 后端：数据库查询使用 `ORDER BY COALESCE(last_message_at, created_at) DESC`，作为初始排序
- 前端：`useEmployeeChat` 中 `conversations` 通过 `useMemo` 从 `allConversations` 派生，每次渲染时本地执行相同排序规则，避免 `last_message_at` 变化时需重新请求后端。仅在结构性变化（创建/删除对话）时调用 `refreshConversationList()` 重新获取全量列表

数据库迁移时自动将已有对话的 `last_message_at` 填充为 `updated_at`

对话导出为 Markdown 文件

### 对话切换性能优化

针对长对话（`messages_json` 体积大、消息数量多）切换时的卡顿问题，前端实现了一套"懒加载 + 内存缓存 + 让出主线程"方案：

- **LRU 消息缓存**：`useEmployeeChat` 用 `LRUCache<string, MessageWithThought[]>` 缓存已解析并处理过的消息数组（已通过 `ensureSegments` + `patchMissingCompletedAt`），容量上限 20 条。切换对话时优先查 LRU，命中则跳过 IPC + `JSON.parse` + 后处理；为避免一次性 mount 大量 `MessageBubble` 阻塞主线程造成可感知的卡顿，命中分支同样先 `setLoadingConversationId` + `setMessages([])` 显示 spinner，再 `await yieldToBrowser()` + `MIN_LOADING_DISPLAY_MS` 至少 120ms 的过渡，最后才 `setMessages(cachedMsgs)`。淘汰按访问时间排序，超过容量时丢弃最久未访问的对话，避免长期使用累积导致内存泄漏
- **懒加载 + 转圈圈**：缓存未命中时立即更新 `activeConversationId`，将 `messages` 清空并设置 `loadingConversationId`，由 `EmployeeWorkbench` 渲染 `<Spin>` 加载态；IPC 拿到数据后通过两次 `await yieldToBrowser()`（`setTimeout(0)`）将 JSON.parse 与 `ensureSegments/patchMissingCompletedAt` 拆开，让 React 在重负载步骤之间有机会先绘制 spinner。设置 `MIN_LOADING_DISPLAY_MS = 120` 避免加载极快时 spinner 闪烁
- **缓存失效**：员工切换时通过 `_persistentMessages.clear()` 清空；删除/清空对话时调用 `deleteConvMessages` 移除单条；切换员工离开时清空所有以避免跨员工缓存污染
- **LRU 工具**：`src/utils/lru-cache.ts` 提供兼容原生 Map 的 LRU 包装（实现了 `entries/keys/values/[Symbol.iterator]`），可被 `for...of` 和解构使用
- **消息列表窗口化渲染**：LRU 缓存命中后，`setMessages(cachedMsgs)` 会一次性把整段长消息塞进 `messages` 状态，此时 React 需要 mount 大量 `MessageBubble`（每个含 `ReactMarkdown` + `CodeBlock`），是切换卡顿的真实耗时点。为此在 `EmployeeWorkbench` 中引入 `visibleCount`（初始 30）控制一次渲染的尾部消息窗口，通过 `useMemo` 切片得到 `visibleMessages`，`visibleStartIndex > 0` 时在消息流顶部展示"查看更早的 N 条消息"链接，点击 `setVisibleCount(prev => prev + 30)`；切换对话时由 `useLayoutEffect` 立即重置 `visibleCount` 并在下一帧 `scrollTop = scrollHeight` 滚到底部，加载更多时 `prevScrollHeightRef` 记录加载前 scrollHeight，`useEffect([visibleCount])` 中补偿 `scrollTop += newScrollHeight - prevScrollHeight` 避免跳动

## 9. LLM 调用日志系统

所有 LLM API 交互自动记录到 JSONL 日志文件，按日期和员工组织目录结构：

```
{dataDir}/.log/llm/{YYYY-MM-DD}/{employeeName}/{conversationId}.jsonl
{dataDir}/.log/llm/{YYYY-MM-DD}/_system.jsonl
```

每条记录包含完整的请求（messages/tools/参数）和响应（content/reasoningContent/toolCalls/usage/latencyMs）信息。使用 AsyncLocalStorage 传递上下文（employeeId/conversationId/source），确保并发异步操作不会混淆。source 标识调用来源：agent/planning/memory_extract/memory_consolidate/knowledge_toc/knowledge_paragraph_summary/knowledge_document_summary/knowledge_global_summary/profiling_analyze/profiling_refine 等。

## 11. KMS 本地知识库搜索引擎

独立模块，位于 `electron/main/services/kms/`，使用独立 SQLite 数据库（`workavatar-kms.db`），与现有知识库系统无耦合。定位为「KMS for AI Agent」——既能独立当桌面搜索工具用，也能作为检索组件接入各类AI智能体。

### 子服务

- **kms-database.service.ts** — KMS独立数据库（索引目录、文件注册表、FTS5索引、向量嵌入、冷热数据、访问追踪）
- **kms-crawler.service.ts** — 目录爬虫（扫描索引目录、检测文件变更、增量索引、访问统计）
- **kms-search-engine.service.ts** — 核心搜索引擎（FTS5全文检索+向量语义+混合搜索+时间范围过滤+文件扩展名过滤）
- **kms-index-manager.service.ts** — 索引管理器（全量/增量/重建索引、向量嵌入生成、冷热数据晋升/降级）
- **kms-search-agent.service.ts** — 独立检索子智能体（LLM驱动的查询分类、检索路径规划、多轮检索、结果提纯）
- **kms-mcp.service.ts** — KMS MCP 服务（Streamable HTTP 传输，将6个检索工具暴露给第三方智能体）
- **kms.service.ts** — 顶层外观服务（组合爬虫/搜索引擎/索引管理器/检索子智能体，提供统一API）

### 冷热数据机制

- **冷数据**：仅索引文件名和关键词，低资源消耗，海量文档可快速上线
- **热数据**：额外生成摘要和段落索引，支持深度语义检索
- **晋升条件**：30天内搜索命中≥5次或读取≥3次 → 冷→热
- **降级条件**：90天无访问 → 热→冷
- 冷启动阶段只构建轻量关键词索引，被频繁访问的文档自动升级为热数据，长期没人访问的热文档自动降级

### 独立检索子智能体

`kms-search-agent.service.ts` 实现内部闭环的检索流程，最终只输出核心结论加精准溯源信息，不挤占主智能体上下文：

1. **查询类型识别**：LLM 自动识别四类需求 → locate（定位查找）/ concept（概念解释）/ trend（趋势梳理）/ analysis（综合分析），匹配对应处理逻辑
2. **检索路径规划**：LLM 根据查询类型规划检索策略（关键词/语义/混合、检索轮次、筛选条件）
3. **多轮检索执行**：按规划自主执行多轮检索，每轮基于前一轮结果补充查找
4. **结果提纯**：LLM 对多轮检索结果进行筛选、去重、提纯，生成结论 + 精准溯源（文件路径、页码、行号、偏移量）
5. **降级策略**：LLM 不可用时降级为单次混合检索 + 关键词摘要

### KMS MCP 服务

`kms-mcp.service.ts` 将本地检索能力暴露为 MCP (Model Context Protocol) 服务，供 Claude Code、Cursor 等主流智能体及自定义 Agent 工作流接入：

- **传输协议**：MCP Streamable HTTP（POST /mcp），兼容 2025-03-26 协议版本
- **暴露工具（6个）**：
  - `kms_list_dirs` — 列出索引目录
  - `kms_stats` — 查看索引统计
  - `kms_search` — 关键词/语义/混合检索
  - `kms_agent_search` — AI 检索子智能体（核心能力，内部闭环输出结论+溯源）
  - `kms_get_content` — 获取文件内容（支持段落ID/偏移/行号定位）
  - `kms_get_summary` — 获取文件摘要
- **配置项**：启用/禁用、端口号（默认3101）、API Key 身份验证
- **设置页面**：全局设置中"本地搜索 MCP"标签页，控制服务启停、端口、API Key，提供客户端配置示例

### 桌面客户端

`src/pages/KMS.tsx` 提供两种搜索视图：

- **普通搜索模式**：关键词/语义/混合三种检索模式，快速返回文件列表，支持目录/格式/时间范围筛选
- **AI 搜索模式**：调用检索子智能体，展示整理后的结论和对应来源（支持直接跳转原文对应位置），可折叠查看检索过程

### IPC通道

19个通道，定义在 `electron/shared/channels/kms.ts`，handler 在 `electron/main/ipc/kms.handlers.ts`，preload API 挂载在 `window.electronAPI.kms`（检索能力）和 `window.electronAPI.kmsMcp`（MCP 服务管理）。
